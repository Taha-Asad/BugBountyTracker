### 1.1 Purpose & Target Scope

This Software Requirements Specification (SRS) defines the consolidated engineering requirements baseline (`Revision 2.8`) for **BugBountyTrack** (`PTUT - PRJ - 089`). It specifies the functional workflows, field-level cryptographic boundaries, authoritative permission matrix, separated researcher and defender key recovery protocols, deterministic severity scoring mathematics, 15-state vulnerability lifecycle finite state machine (FSM), formal Use Case specifications, and quantifiable non-functional acceptance targets (latency, security, and uptime) for our Final Year Project prototype, structured in accordance with **IEEE Std 830-1998** and **ISO/IEC/IEEE 29148:2018**.

* **Requirement & Priority Conventions**: Every requirement and atomic subrequirement in this specification has a unique, testable identifier (`FR-X.Y`, `FR-X.Ya`, `NFR-XX`, `UC-XX`) and is assigned a build-consistent priority so that **no P1 requirement or main use-case success scenario ever depends on a P2 component**:

### 1.4 Finalized One-Paragraph Problem Statement & Discovery Evidence Summary

#### 1.4.1 Finalized One-Paragraph Academic Problem Statement

> **While established vulnerability platforms and source-code hosts offer free entry tiers (such as HackerOne Essential VDP, which documents AES-256 encryption at rest and TLS in transit, or GitHub Security Advisories), they operate on a provider-managed encryption model where the platform vendor holds the decryption keys and processes plaintext exploit payloads on its servers, or are coupled to single-forge repository ecosystems. Small and medium software engineering teams (5–50 developers) unwilling to grant third-party platform servers decryptable access to zero-day exploit payloads typically fall back to ad-hoc communication channels (such as generic `security@company.com` email inboxes, shared spreadsheets, or standard issue trackers) that lack mandatory end-to-end payload encryption across shared mailboxes and mail relays unless external reporters manually configure PGP—deterring ethical researchers due to missing RFC 9116 (`security.txt`) discovery manifests linked to published scope and Safe Harbor policies, mandatory account registration friction, and subjective ad-hoc severity negotiation. Furthermore, existing issue trackers and entry-level VDP tiers treat vulnerability resolution as an informal text status toggle ('Closed' or 'Resolved'), creating a 'fix-and-forget' verification gap where patches are deployed without verifiable Git commit linkage or attested researcher retesting. BugBountyTrack resolves these gaps by delivering a lightweight, multi-tenant Vulnerability Disclosure Platform (VDP) that automates browser-signed RFC 9116 `security.txt` discovery linked to hosted Safe Harbor policies, enforces client-side OpenPGP v6 (`Curve25519`) exploit payload encryption so decryption keys remain outside normal server processing and the platform stores ciphertext only, provides deterministic FIRST.org CVSS v3.1 scoring with researcher-visible explanations, and governs remediation through an evidence-based, Git-linked retest state machine.**

## 2. Overall Description, Cryptographic Boundary & Permission Model

### 2.1 System Context & Logical Boundaries

BugBountyTrack is organized into three logical tiers (detailed 3-Tier Architecture and Level 0 / Level 1 Data Flow Diagrams are specified in the Week 3 Architecture Deliverable):
1. **Client Browser Runtime**: Next.js 14+ App Router, React 18+, Tailwind CSS, `OpenPGP.js v6` client-side encryption, decryption, session-key wrapping, and detached signing, `rehype-sanitize` Markdown AST sanitizer, and WebCrypto API (`crypto.subtle.digest` for SHA-256 hashing).
2. **Application API Gateway & Scheduled Worker**: Next.js Route Handlers running on Node.js 22 LTS, enforcing the Authoritative Permission Matrix (`Table 2.2`), database-persisted sessions, OpenPGP v6 detached signature (`X-Guest-Signature`) and HMAC (`X-Cron-Signature`) verification prior to PostgreSQL invocation, optimistic concurrency checks (`recipient_set_version`, `report_recipient_version`, and `state_version`), atomic single-use submission sessions, upload quota reservations, GitHub REST API v3 commit/branch comparisons, and a 3-phase hourly lifecycle/cleanup cron endpoint triggered by an authenticated GitHub Actions scheduled workflow.
3. **Persistence & Object Storage Layer**: Neon Serverless PostgreSQL 16 (isolated inside schema `bbt_core`, enforcing `FORCE ROW LEVEL SECURITY` under non-superuser runtime role `bbt_app_runtime`, hardened `SECURITY DEFINER` entrypoints under `bbt_fn_owner`, `organization_audit_heads` serialization, and an append-only hash-chained `audit_events` ledger) and Cloudflare R2 (storing client-encrypted OpenPGP binary PoC attachments within a hard cluster-wide `9.5 GiB` cap).

### 2.2 Defensible Protection Boundary, Cryptographic Pinning & Explicit Limitations

Rather than claiming blanket "zero-knowledge" across the entire application, BugBountyTrack defines an explicit **Client-Side End-to-End Encrypted (E2EE) Payload Isolation Boundary**:

* **What Is Cryptographically Isolated from the Server**: All sensitive vulnerability text, files, and cached guest credentials (classified as **Class B** and **Class C** in Table 2.1—including report titles, vulnerability descriptions, reproduction steps, PoC attachments, discussion messages, internal reviewer notes, researcher-visible CVSS explanations, internal CVSS notes, rejection explanations, risk-acceptance rationales, remediation summaries, configuration snapshots, retest notes, administrative audit justifications, and cached guest `access_token` retry envelopes) are encrypted in the client browser (or encrypted to `REPORT.guest_public_key` before caching) using OpenPGP v6 packets. The backend server, PostgreSQL database, and Cloudflare R2 store ciphertext only for these payloads.
* **What the Server Intentionally Knows (Class A Operational Metadata)**: To route reports, enforce tenant and cluster quotas, calculate SLA deadlines, verify Git commits, and maintain a deterministic state machine, the server stores and processes plaintext operational metadata: organization/program identifiers, actor IDs, timestamps, workflow state (`state`, `state_version`), a coarse 8-value category enum (`operational_label`), target asset identifier (`asset_scope`), CVSS v3.1 vector string and numeric score (`cvss_vector`, `cvss_score`), remediation reference metadata (`commit_sha`, `branch_name`, `config_hash`, `deployment_env`), and cryptographic hashes. Because Class A fields such as `asset_scope`, `branch_name`, `organization_id`, and `hunter_id` can still be operationally sensitive outside the tenant, external exports are further restricted by the strict **External Export Allowlist** in Table 2.1 and `FR-7.7`.
* **Standardized `OpenPGP.js v6` Configuration & Native Formats (`s2kType = argon2`)**:
  * All keys and encrypted containers are standardized on **RFC 9580 OpenPGP Version 6 Curve25519 (`Ed25519` primary signing key + `X25519` encryption subkey)** with **64-character hexadecimal SHA-256 fingerprints**, avoiding custom cryptographic envelopes.
  * Because `OpenPGP.js v6` only applies `s2kArgon2Params` when Argon2 is explicitly selected as the S2K type, the client cryptographic module explicitly configures:
    1. `openpgp.config.v6Keys = true` (RFC 9580 v6 key packets and SEIPDv2 AEAD encrypted data packets)
    2. **`openpgp.config.s2kType = openpgp.enums.s2k.argon2`** (explicitly selecting RFC 9580 Argon2id String-to-Key specifier `0x04`)
    3. `openpgp.config.s2kArgon2Params = { passes: 3, parallelism: 4, memoryExponent: 16 }` (`2^16 KiB = 65,536 KiB = 64 MiB` RAM)
    4. `openpgp.config.aeadProtect = true` (authenticated encryption for secret keys and symmetric messages)
* **Key-Versioned Report Recipients (`REPORT_RECIPIENT` & `report_recipient_version`)**:
  * At initial report submission, the server snapshots the program's active `PROGRAM_DEFENDER` key records (`user_id`, `key_id`, `key_fingerprint`) into `REPORT_RECIPIENT` for that report, records the submitter's active key reference (`submitter_key_id` for `HUNTER` or `guest_public_key` for `GUEST`), and initializes `REPORT.report_recipient_version = 1`.
  * Every subsequent encrypted write on that report (comments, internal notes, CVSS explanations/notes, remediation notes, configuration snapshots, retest evidence, or follow-up attachments) must generate a **fresh random 256-bit OpenPGP session key**, encrypt strictly for the authoritative recipient set of its data class (Class B: Active `REPORT_RECIPIENT` keys + `PROGRAM.recovery_public_key` + Submitter Active Key; Class C: Active `REPORT_RECIPIENT` keys + `PROGRAM.recovery_public_key`), and submit `report_recipient_version`.
  * Whenever a defender is removed from a program, removed from an organization, or has a key revoked—or whenever a registered researcher replaces their `submitter_key_id`—the server atomically increments `REPORT.report_recipient_version` on every affected report, rejecting any in-flight write encrypted to a stale recipient list with HTTP `409 Conflict`.
* **Explicit Cryptographic & Runtime Limitations**:
  1. *Browser Code & Key-Distribution Trust*: Within the web security model, the client browser trusts the application bundle delivered over HTTPS (hardened with Subresource Integrity and strict Content Security Policy) and the server's public-key directory endpoint. To detect silent public-key substitution by a compromised server, researchers can cross-verify the organization's 64-character public key fingerprint against the cleartext-signed `https://[org-domain]/.well-known/security.txt` hosted on the organization's own domain (`FR-2.3`).
  2. *Prior-Access Revocation Limitation*: Deactivating a defender in `PROGRAM_DEFENDER` and `REPORT_RECIPIENT` immediately blocks their API access and excludes their key from future encrypted objects, but **cannot retroactively erase ciphertext or decrypted keys that the defender downloaded to their local machine prior to revocation**.
  3. *JavaScript Memory Hygiene Limitation*: On logout or key lock, the client explicitly overwrites owned `Uint8Array` buffers (`fill(0)`), deletes ephemeral keys from `IndexedDB` when requested, and nullifies references (`nullified`). Because JavaScript strings are immutable and garbage-collected asynchronously, this is a **best-effort defense-in-depth measure** and cannot guarantee physical RAM page zeroization against local OS memory dumps.

### 2.6 Hourly Cron Authentication, 3-Phase Claim-Lease R2 Cleanup with Per-Batch Finalization & DB Timeouts, Logical vs. Physical Database Capacity & PL/pgSQL Subtransaction Atomic Pause

* **Single Authoritative Hourly Cron Authentication Contract (`X-Cron-Timestamp` + `X-Cron-Signature`) & 3-Phase Claim-Lease Execution with Per-Batch Finalization and Enforceable DB Timeouts**:
  * Because Vercel Hobby limits native `vercel.json` cron expressions to once per day (`0 0 * * *`), the hourly SLA, inactivity timeout, expired session/nonce purge, and expired upload reservation job (`0 * * * *`) is triggered by an **external GitHub Actions Scheduled Workflow (`lifecycle-cron.yml`)** sending `POST /api/cron/lifecycle-evaluate`.
  * **Unified Authentication Contract**: Every cron request must include two headers verified in the Node.js route handler before opening any database connection:
    1. `X-Cron-Timestamp`: Current Unix epoch timestamp in seconds (integer string). The server rejects any request where `abs(now_epoch_sec - int(X-Cron-Timestamp)) > 300` (5-minute replay window) with HTTP `401 Unauthorized`.
    2. `X-Cron-Signature`: `sha256=<64-hex-hmac>`, computed as `HMAC_SHA256(CRON_HMAC_SECRET, X-Cron-Timestamp + "." + raw_request_body)` and verified on the server using constant-time `crypto.timingSafeEqual`. (No `Authorization: Bearer` header is used for cron authentication.)
  * **3-Phase Claim-Lease Cron Execution (`Phase 1 -> Phase 2 -> Phase 3` Sequentially Per Batch), Enforceable DB Timeouts & Reserved `4,000 ms` Finalization Headroom (`15,000 ms` Route Ceiling)**: To prevent PostgreSQL locks from spanning Cloudflare R2 HTTP calls, bound expired-session/nonce deletions, and **ensure that a worker crash, DB timeout, or invocation timeout after Phase 1 or Phase 2 can never leave a reservation permanently stuck in `'DELETING'` (`FR-5.4`, `FR-8.4`, `UC-07`)**, `bbt_core.upload_reservations` includes **`claim_id UUID NULL`** and **`claim_expires_at TIMESTAMPTZ NULL`**. Because SQL `LIMIT` clauses (`10` R2 claims, `50` deadlines, `200` purges) bound **work volume** rather than guaranteed wall-clock duration, `<= 400 ms` for Phase 1 and Phase 3 is defined as a **measurable performance target backed by enforceable client and PostgreSQL timeout budgets**: every cron DB transaction acquires its pooled connection with **`connectionTimeoutMillis = 1,000 ms`** and immediately sets **`SET LOCAL lock_timeout = '250ms'; SET LOCAL statement_timeout = '800ms';`** (plus a hard client-side query abort at `t == 14,500 ms`). Each batch executes **sequentially (`Phase 1 -> Phase 2 -> Phase 3`)**:
    1. *Phase 1 — Short Database Transaction #1 (`fn_cron_evaluate_overdue_deadlines(now(), p_deadline_limit => 50, p_r2_claim_limit => 10, p_purge_limit => 200)` — Target `<= 400 ms`, Enforced `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)*: Acquires `pg_try_advisory_xact_lock(889001)` (exiting immediately if another cron worker is active), purges up to **`p_purge_limit => 200` expired `submission_sessions` rows** (`WHERE expires_at < now() ORDER BY expires_at ASC LIMIT 200 FOR UPDATE SKIP LOCKED`) and up to **`p_purge_limit => 200` expired `guest_mutation_nonces` rows** (`WHERE expires_at < now() ORDER BY expires_at ASC LIMIT 200 FOR UPDATE SKIP LOCKED`), processes up to **`p_deadline_limit => 50` overdue SLA / `NEED_MORE_INFO` timeout records** (`ORDER BY id ASC LIMIT 50 FOR UPDATE SKIP LOCKED`, skipping any report where `capacity_deadline_paused = true`), and claims up to **`p_r2_claim_limit => 10` expired or lease-timed-out `upload_reservations` rows**:
       `WHERE (status IN ('RESERVED', 'DELETE_FAILED') AND expires_at <= now()) OR (status = 'DELETING' AND claim_expires_at <= now()) ORDER BY reservation_id ASC LIMIT 10 FOR UPDATE SKIP LOCKED`,
       atomically setting **`status = 'DELETING'`, `claim_id = gen_random_uuid()`, and `claim_expires_at = now() + interval '2 minutes'`** and returning `(reservation_id, claim_id, organization_id, r2_object_key, exact_ciphertext_bytes)` plus `has_more_deadline_backlog BOOLEAN`, `has_more_r2_backlog BOOLEAN`, `has_more_purge_backlog BOOLEAN`, and the unified **`has_more_backlog = (has_more_deadline_backlog OR has_more_r2_backlog OR has_more_purge_backlog)`** before committing Tx #1.
    2. *Phase 2 — Node.js Cloudflare R2 I/O Outside Any DB Transaction with `1,000 ms` Per-Request Timeout & Hard `11,000 ms` Invocation Cutoff (`10` objects at concurrency `5` = `2` waves × `<= 1,000 ms` = `<= 2,000 ms` [`<= 2.2s` with overhead] per batch)*: For each of the `<= 10` claimed reservations in the current batch, the Node.js handler executes `DeleteObjectCommand` against Cloudflare R2 with **bounded concurrency `5` (`<= 2` waves per 10-object batch)** and a combined abort signal **`AbortSignal.any([AbortSignal.timeout(1000), AbortSignal.timeout(Math.max(0, 11000 - elapsed_ms))])`** enforcing both a **`1,000 ms` (`1.0s`) per-request timeout** and a **hard invocation-wide R2 I/O cutoff at `t == 11,000 ms`** (so `11,000 ms .. 15,000 ms` [`4,000 ms`] remains available as reserved invocation headroom if the final batch's Phase 2 runs up to `t == 11,000 ms`). Both HTTP `204 No Content` and `404 Not Found` (object never uploaded or already removed by an earlier crashed/timed-out worker) count as confirmed physical deletion; transient network/5xx errors or any request timed out (`> 1,000 ms`) or aborted/unstarted at the `11,000 ms` invocation cutoff are marked for `'DELETE_FAILED'`.
    3. *Phase 3 — Immediate Per-Batch Database Transaction #2 (`fn_cron_finalize_r2_deletions` — Target `<= 400 ms`, Enforced `connectionTimeoutMillis = 1,000 ms`, `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)*: **Executed immediately after the current batch's Phase 2 finishes (not delayed until second 11)**—and guaranteed at least `4,000 ms` (`11,000 ms .. 15,000 ms`) of remaining invocation time even when the last batch's Phase 2 hits the `11,000 ms` cutoff—Phase 3 acquires locks in canonical order (`1. cluster_storage_state FOR UPDATE -> 2. organizations ORDER BY id ASC FOR UPDATE`), matches **`WHERE reservation_id = :res_id AND status = 'DELETING' AND claim_id = :claim_id`**, transitions confirmed deletions to `status = 'DELETED', deleted_at = now()`, and **credits back `exact_ciphertext_bytes` to `organizations.r2_bytes_used` and `cluster_storage_state.total_r2_allocated_bytes` strictly when `status = 'DELETING' AND claim_id = :claim_id` transitions to `'DELETED'` (`ROW_COUNT == 1`)** (and sets `status = 'DELETE_FAILED', claim_id = NULL, claim_expires_at = NULL` without crediting bytes for any failed, timed-out, or cutoff-aborted R2 request, setting `has_more_r2_backlog = true` and `has_more_backlog = true`). **Uncommitted Finalization & Timeout Recovery**: If Phase 3 cannot acquire a DB connection (`1,000 ms`), exceeds `lock_timeout` (`250 ms`, `SQLSTATE '55P03'`) or `statement_timeout` (`800 ms`, `SQLSTATE '57014'`), or fails to commit before the `14,500 ms` client abort / `15,000 ms` route ceiling, the transaction rolls back, the handler **does not report those rows as finalized**, sets `has_more_r2_backlog = true` (`has_more_backlog = true`), and leaves the rows in `'DELETING'` so their 2-minute lease (`claim_expires_at`) expires; a subsequent run then reclaims the rows with a fresh `claim_id`, R2 `DeleteObjectCommand` idempotently returns `204` or `404`, and Phase 3 transitions `'DELETING' -> 'DELETED'` and credits bytes **strictly once** (while any late-waking worker with a superseded `claim_id` matches `0` rows and credits `0` bytes).
    4. *Multi-Batch Loop (`<= 3` Sequential `Phase 1 -> Phase 2 -> Phase 3` Batches, Starting Only When `elapsed_ms <= 8,000 ms`) & Unified `has_more_backlog` Continuation*: Within a single `POST /api/cron/lifecycle-evaluate` invocation, the handler executes `Phase 1 -> Phase 2 -> Phase 3` sequentially for up to **`3` batches (`<= 30` R2 objects, `<= 150` deadlines, and `<= 600` session/nonce purges per invocation)**, starting a new batch **only while `has_more_backlog == true` AND `elapsed_ms <= 8,000 ms`** (so Batches 1 and 2 finalize immediately after their own Phase 2, and even a 3rd batch starting at `8,000 ms` ceases R2 I/O by `11,000 ms` with `4,000 ms` of remaining invocation time reserved for its Phase 3 finalization). Whenever **`has_more_backlog == true`** (`has_more_deadline_backlog OR has_more_r2_backlog OR has_more_purge_backlog`) when the route returns (`{ status: "ok", has_more_backlog, has_more_deadline_backlog, has_more_r2_backlog, has_more_purge_backlog }`), `lifecycle-cron.yml` immediately triggers a follow-up `workflow_dispatch` invocation (up to `10` chained runs) so multi-hundred-row deadline, purge, or R2 backlogs are drained within minutes.
* **Achievable Cluster & Tenant Storage Capacity Rules (`MiB` / `GiB` Binary Accounting)**:
  * To prevent tenant allocations from exceeding physical Free Tier limits across `<= 10` evaluation tenants, the system enforces **both per-tenant and cluster-wide hard caps** backed by exact byte accounting:
  * **1. Cloudflare R2 Object Storage Budget (`10 GB` Physical Tier / `9.5 GiB` [`10,200,547,328 bytes`] Hard Cluster Allocation Limit)**:
    - Each tenant has a per-tenant R2 cap of **`1.0 GiB` (`1,024 MiB` / `1,073,741,824 bytes`)** (with `<= 2.0 GiB` configurable for a single benchmark tenant only if cluster headroom permits), and the singleton table `bbt_core.cluster_storage_state (id = 1, total_r2_allocated_bytes BIGINT, emergency_db_buffer_used_bytes BIGINT)` enforces a **hard cluster-wide R2 allocation ceiling of `9.5 GiB` (`10,200,547,328 bytes`)** covering the sum of all active `RESERVED`, `DELETING`, `DELETE_FAILED` (`upload_reservations`) and `BOUND` (`attachments`) objects across all tenants.
    - During `POST /api/uploads/presign`, following the universal canonical lock order (`1. cluster_storage_state -> 2. organizations`), the server locks `cluster_storage_state (id = 1)` and the tenant's `organizations` row `FOR UPDATE`: if adding `exact_ciphertext_bytes` would exceed either the tenant's `1.0 GiB` R2 quota (`TENANT_R2_QUOTA_EXCEEDED`) or the cluster's `9.5 GiB` R2 ceiling (`CLUSTER_R2_CAPACITY_EXCEEDED`), the presign request is atomically rejected with HTTP `413 Payload Too Large`.
  * **2. Neon PostgreSQL Storage Budget (`512 MiB` [`536,870,912 bytes`] Physical Ceiling)**:
    - **Bucket A — Per-Tenant Logical Intake Pool (`20 MiB` [`20,971,520 bytes`] per tenant; `200 MiB` across 10 tenants) with `1.0 MiB` Active-Report Researcher Response Sub-Reserve**:
      1. *Tracked Tables*: Tracks external researcher and intake data (`programs`, `submission_sessions`, `upload_reservations`, `reports` root columns, `attachments` metadata, `discussion_messages` in `RESEARCHER_ORG` submitted by researchers, and `retest_evidence` submitted by researchers).
      2. *`90%` Warning (`18.0 MiB` / `18,874,368 bytes`)*: Emits a tenant dashboard warning (`INTAKE_QUOTA_90_PERCENT`).
      3. *`95%` New-Submission Ceiling (`19.0 MiB` / `19,922,944 bytes`) vs. `5%` (`1.0 MiB` / `1,048,576 bytes`) Active-Report Researcher Response Sub-Reserve*: To ensure that a flood of new reports can **never block an existing researcher from replying to a `NEED_MORE_INFO` request (`FR-7.5`) or submitting a `VERIFIED_RESEARCHER` / `RETEST_FAILED` attestation (`FR-7.2`, `FR-7.4`) and falsely manufacture "researcher inactivity"**, **new report submissions (`POST /api/v1/reports`) and new attachment presigns (`POST /api/uploads/presign`) are capped at `95%` (`19.0 MiB` / `19,922,944 bytes`)** and rejected above that threshold with HTTP `413 Payload Too Large: NEW_REPORT_INTAKE_QUOTA_EXCEEDED`. The final **`5%` (`1.0 MiB` / `1,048,576 bytes`, sufficient for `>= 64` researcher responses at `<= 16 KiB` each)** is reserved exclusively for compact (`<= 16 KiB`) researcher actions on existing active reports (`NEED_MORE_INFO` replies, `VERIFIED_RESEARCHER` confirmations, `RETEST_FAILED` attestations, and `WITHDRAWN` retractions).
      4. *Client-Owned Outer Transaction & PL/pgSQL Nested `BEGIN ... EXCEPTION` Subtransaction Pause Under Held Lock (`bbt_core.fn_process_researcher_response_or_pause`) & Logical Quota Lock vs. Physical DB Exhaustion*:
         - **Why a Client-Owned Outer Transaction, PL/pgSQL Subtransaction Block, and Narrow Logical Exemption Are Required (PostgreSQL MVCC & Function Transaction Rules)**: In PostgreSQL MVCC, every `UPDATE` allocates a new physical row version (heap tuple), and setting `capacity_paused_at` from `NULL` to a non-null `TIMESTAMPTZ` alters the row's null bitmap/tuple size; even a Heap-Only Tuple (HOT) update requires free space on the target page. Furthermore, in PostgreSQL 16 PL/pgSQL, a **function cannot execute top-level `COMMIT` or `ROLLBACK`, and ending a transaction is prohibited inside an `EXCEPTION` block**; instead, a nested PL/pgSQL **`BEGIN ... EXCEPTION WHEN ... END` block** creates an internal PostgreSQL subtransaction whose partial writes automatically roll back when the `EXCEPTION` handler is entered while **preserving locks acquired before the inner block in the outer transaction**. Accordingly, **the Node.js API / database client owns the outer transaction (`BEGIN ... COMMIT` or `ROLLBACK`)**, while `bbt_core.fn_process_researcher_response_or_pause` acquires and holds the `2. organizations FOR UPDATE -> 5. reports FOR UPDATE` locks, executes the researcher payload write inside a nested PL/pgSQL `BEGIN ... EXCEPTION` subtransaction block, and returns a structured JSONB outcome for the API client to commit.
         - **Step 1 — Client-Owned Outer `BEGIN`, Canonical Lock & Terminal/Invalid State Pre-Check (`HTTP 409 Conflict`)**: The Node.js API client opens the outer transaction (`BEGIN`), and `bbt_core.fn_process_researcher_response_or_pause` resets all `app.definer_*` and `app.quota_exempt_reason` GUCs, locks **`2. organizations FOR UPDATE -> 5. reports FOR UPDATE`**, and inspects `reports.state` and `reports.state_version`. If the report has **already legitimately transitioned to a terminal state (`CLOSED_INCOMPLETE`, `CLOSED_UNVERIFIED_TIMEOUT`, `VERIFIED_RESEARCHER`, `VERIFIED_INTERNAL`, `WITHDRAWN`, etc.) or is no longer in the required active state (`NEED_MORE_INFO` or `RETEST_PENDING`) before the researcher request obtained its lock** (or `state_version` mismatches), the function **does not set `capacity_deadline_paused = true` and does not mutate the report**, returning structured JSONB `{"outcome": "CONFLICT_409", "http_status": 409, "error_code": "REPORT_STATE_CONFLICT_OR_ALREADY_CLOSED", "deadline_paused": false}`; the API client commits/ends the read-only transaction and returns **`HTTP 409 Conflict`**.
         - **Step 2 — Nested PL/pgSQL `BEGIN ... EXCEPTION WHEN SQLSTATE 'P0001'` Subtransaction & Narrow Logical Quota Exemption Under Held Lock (`413` / `507` with `"deadline_paused": true` Sent Only After Outer `COMMIT`)**: While holding the outer transaction's `FOR UPDATE` locks on `organizations` and `reports`, the function enters a nested PL/pgSQL **`BEGIN ... EXCEPTION WHEN SQLSTATE 'P0001' THEN ... END` subtransaction block** and attempts the researcher write. If the logical quota check passes, the inner block inserts the response, clears any prior pause (`capacity_deadline_paused = false, capacity_paused_at = NULL`), updates report state/deadlines, locks `6. organization_audit_heads FOR UPDATE` to append `audit_events`, and returns `{"outcome": "APPLIED", "http_status": 200, "deadline_paused": false}`, which the API client **`COMMIT`s** before returning `200 OK` / `201 Created`. If `trg_enforce_tenant_db_quota` raises `SQLSTATE 'P0001'`, PostgreSQL automatically rolls back the inner `BEGIN` block's partial writes (while **retaining the outer `FOR UPDATE` locks on `organizations` and `reports`**) and enters the `EXCEPTION WHEN SQLSTATE 'P0001'` handler. The handler inspects `SQLERRM` / `PG_EXCEPTION_DETAIL`: **if the error is not one of the four recognized logical quota codes (`TENANT_INTAKE_QUOTA_EXCEEDED`, `NEW_REPORT_INTAKE_QUOTA_EXCEEDED`, `SECURITY_RESERVE_PRIORITY0_ONLY`, `TENANT_SECURITY_RESERVE_EXHAUSTED`), it immediately executes `RAISE;` so unrelated `P0001` or other errors propagate and abort the outer transaction**. For a recognized logical quota code, the handler executes `PERFORM pg_catalog.set_config('app.quota_exempt_reason', 'CAPACITY_DEADLINE_PAUSE', true);`, updates `bbt_core.reports SET capacity_deadline_paused = true, capacity_paused_at = COALESCE(capacity_paused_at, now()), updated_at = now()`, resets `app.quota_exempt_reason` to `''`, and returns structured JSONB `{"outcome": "PAUSED_QUOTA", "http_status": 413 | 507, "error_code": <quota_code>, "deadline_paused": true}`. **The Node.js API client then executes `COMMIT` on the outer transaction and sends HTTP `413 Payload Too Large` or `507 Insufficient Storage` with `"deadline_paused": true` strictly after `COMMIT` succeeds.** While `capacity_deadline_paused = true`, both `NEED_MORE_INFO -> CLOSED_INCOMPLETE` (`FR-7.5`) and `RETEST_PENDING -> CLOSED_UNVERIFIED_TIMEOUT` (`FR-7.2`) are blocked. When tenant capacity recovers below `95%`, the resumed deadline is set to **`GREATEST(existing_due + (now() - capacity_paused_at), now() + interval '7 days')`** (`capacity_deadline_paused = false, capacity_paused_at = NULL`), guaranteeing at least a 7-day post-recovery grace window while **never shortening a longer remaining deadline**.
         - **Step 3 — Physical Database Storage Exhaustion Fallback (`SQLSTATE '53100' disk_full` -> Outer `ROLLBACK` & `HTTP 503 Service Unavailable`, `"deadline_paused": false`)**: If physical PostgreSQL / Neon disk space is exhausted (`SQLSTATE '53100' disk_full` or storage read-only engine error, which is not caught by `WHEN SQLSTATE 'P0001'`) such that the function or outer `COMMIT` fails physically, the Node.js API client issues `ROLLBACK` on the outer transaction, returns **`HTTP 503 Service Unavailable` (`{"error": "DATABASE_PHYSICAL_STORAGE_EXHAUSTED", "deadline_paused": false, "retryable": true}`)**, and emits an immediate operational alert (`PHYSICAL_DB_STORAGE_CRITICAL`) rather than claiming a pause was persisted when the database physically could not write.
    - **Bucket B — Per-Tenant Security, Triage & Remediation Reserve (`6 MiB` [`6,291,456 bytes`] Base Reserve per tenant; `60 MiB` across 10 tenants)**: Tracks internal defender and security operations (`organization_audit_heads`, `audit_events`, `cvss_assessment_history`, `discussion_messages` in `REVIEWER_INTERNAL` and defender-authored `RESEARCHER_ORG` messages, `remediation_records` [with raw incompressible UTF-8 plaintext input capped at **`<= 160 KiB` (`163,840 bytes`)** with compression disabled and armored `config_artifact_ciphertext` capped at **`<= 256 KiB` (`262,144 bytes`)** per record], defender-submitted `retest_evidence`, and `guest_mutation_nonces`).
    - **Bounded Reserve Priority, Exact Floor Arithmetic & Separated Resource Recovery Rules (Testable Guarantee)**:
      1. *`80%` Reserve Warning (`4.8 MiB` / `5,033,165 bytes`)*: Emits a high-priority dashboard banner and `notification_outbox` alert (`SECURITY_RESERVE_80_PERCENT`).
      2. *Priority-0 Critical Security Floor at `5,984,256 bytes` (Deliberate `300 KiB` [`307,200 bytes`] Floor; Exact `5%` of `6 MiB` is `307.2 KiB` [`314,573 bytes`], Rounded to `300 KiB`)*: Whenever a write would cause `db_reserve_bytes_used` to exceed **`5,984,256 bytes`** (leaving the final **`300 KiB` / `307,200 bytes` Priority-0 floor**, sufficient for `>= 500` compact state/key/audit records at `<= 600 bytes` each), the server rejects **ALL non-critical reserve writes of any size**—including `CONFIG_INFRASTRUCTURE` snapshots, `REVIEWER_INTERNAL` notes, non-closing defender comments, and new fix proposals—with HTTP `413 Payload Too Large: SECURITY_RESERVE_PRIORITY0_ONLY`. Within this final `300 KiB` (`307,200 bytes`) reserve band (`5,984,256` to `6,291,456 bytes`), **only the explicit Priority-0 Critical Security Allowlist is permitted**: (i) defender/member/key revocations and offboarding (`FR-3.8a`), (ii) guest token rotations (`FR-1.6e`), (iii) **researcher clarification replies (`NEED_MORE_INFO -> TRIAGING`, `FR-7.5`)**, (iv) terminal lifecycle closures and `RETEST_FAILED` loopbacks (`FR-7.1`–`FR-7.4`), and (v) their mandatory `audit_events` rows.
      3. *`100%` Reserve Exhaustion (`6.0 MiB` / `6,291,456 bytes`), Resource Pool Separation & Bounded Emergency Reserve Buffer (`<= +2 MiB` per tenant from `20 MiB` Cluster Buffer)*: If the tenant's security reserve reaches `100%` (`db_reserve_bytes_used >= db_reserve_quota_bytes`), the tenant enters a deterministic **`READ_ONLY_CAPACITY_LOCK`** state and normal mutating database requests fail closed with HTTP `507 Insufficient Storage: TENANT_SECURITY_RESERVE_EXHAUSTED` (except the narrow PL/pgSQL `EXCEPTION` pause branch inside `bbt_core.fn_process_researcher_response_or_pause` and the MFA-verified `ORG_OWNER` recovery endpoints below). **Explicit Separation of Resource Pools**: Purging expired `upload_reservations` (`DELETE /api/v1/organizations/{id}/reservations/expired`) or deleting R2 attachments frees **`r2_bytes_used` and `db_intake_bytes_used`**, whereas `guest_mutation_nonces` purge frees only expired nonce rows in **`db_reserve_bytes_used`**. Because `audit_events` rows are append-only (`0` `DELETE` privilege) and logical quota numbers cannot create physical disk space beyond Neon's `512 MiB` ceiling, `cluster_storage_state` maintains a dedicated, pre-budgeted **`20 MiB` (`20,971,520 bytes`) Shared Emergency DB Reserve Buffer** (`emergency_db_buffer_used_bytes`). An MFA-verified `ORG_OWNER` invoking `PATCH /api/v1/admin/organizations/{id}/quota` may allocate emergency reserve headroom from this buffer **strictly in `1 MiB` (`1,048,576 bytes`) increments up to a hard per-tenant maximum of `+2 MiB` (`8 MiB` / `8,388,608 bytes` total `db_reserve_quota_bytes`)**, subject to `cluster_storage_state.emergency_db_buffer_used_bytes + 1,048,576 <= 20,971,520 bytes` and physical `pg_database_size(current_database()) < 450 MiB` (`471,859,200 bytes`).
    - **Bucket C — Shared Emergency DB Reserve Buffer (`20 MiB` [`20,971,520 bytes`]) + Budgeted Index, TOAST, WAL & Shared-Table Overhead (`232 MiB` [`243,269,632 bytes`])**: Subtracting `200 MiB` (10 × `20 MiB` intake pools), `60 MiB` (10 × `6 MiB` base security reserves), and `20 MiB` (cluster-wide Shared Emergency DB Reserve Buffer) from the `512 MiB` Neon physical ceiling leaves **`232 MiB` (`243,269,632 bytes`) budgeted for overhead and shared storage** (PostgreSQL B-tree indexes, TOAST tables, shared tables [`users`, `sessions`, `notification_outbox`], and Neon WAL metadata); **actual remaining physical capacity is continuously monitored** via `SELECT pg_database_size(current_database())` on `/api/v1/health` (emitting warnings at `400 MiB` physical usage and blocking emergency reserve expansion at `450 MiB`).
    - **Projected Post-Write Byte Accounting & Narrowly Scoped Logical Quota Exemption (`INSERT`, `UPDATE`, `DELETE`)**: Because every mutating transaction locks `2. organizations FOR UPDATE` near the start of the transaction (`FR-7.1b`), `organizations.db_intake_bytes_used` and `organizations.db_reserve_bytes_used` are maintained atomically by the PostgreSQL `AFTER INSERT OR UPDATE OR DELETE` row trigger `trg_enforce_tenant_db_quota` computing `delta_bytes = COALESCE(pg_column_size(NEW), 0) - COALESCE(pg_column_size(OLD), 0)`. **Narrowly Scoped Logical Quota Exemption (`app.quota_exempt_reason = 'CAPACITY_DEADLINE_PAUSE'`)**: When `current_setting('app.quota_exempt_reason', true) = 'CAPACITY_DEADLINE_PAUSE'` during an `UPDATE` on `bbt_core.reports` (set exclusively inside the `EXCEPTION WHEN SQLSTATE 'P0001'` handler of `bbt_core.fn_process_researcher_response_or_pause` after the inner `BEGIN` block rolls back), `trg_enforce_tenant_db_quota` verifies that **every column of `NEW` and `OLD` is identical (`IS NOT DISTINCT FROM`) except `capacity_deadline_paused`, `capacity_paused_at`, and `updated_at`**; when that column-invariance check holds, the trigger records `delta_bytes` in `db_intake_bytes_used` **without raising a logical quota exception**, permitting the pause metadata update to commit in the outer transaction inside the tenant's logical capacity lock so long as physical database storage is available. For all non-exempt writes where `delta_bytes > 0`, the trigger asserts that the **projected post-write total (`current_bytes + delta_bytes`) does not exceed the applicable logical threshold ceiling** (`19,922,944 bytes` for new report intake, `20,971,520 bytes` for active-report researcher responses, `db_reserve_quota_bytes - 307,200` for non-Priority-0 reserve writes, and `db_reserve_quota_bytes` for Priority-0 reserve writes); if exceeded, the trigger raises `SQLSTATE 'P0001'` with the specific logical quota code (`NEW_REPORT_INTAKE_QUOTA_EXCEEDED`, `TENANT_INTAKE_QUOTA_EXCEEDED`, `SECURITY_RESERVE_PRIORITY0_ONLY`, or `TENANT_SECURITY_RESERVE_EXHAUSTED`), distinct from PostgreSQL's physical `SQLSTATE '53100'` (`disk_full`).

## 3. Specific Functional Requirements (FR)

### 3.1 Multi-Tenant Workspaces, Onboarding, Guest Intake & Access Governance (`FR-1`)

* **FR-1.1 (P1, Core — Multi-Tenant Isolation & Composite Foreign Keys)**: The system shall isolate organization workspaces using an `organization_id` column on all tenant-scoped tables in schema `bbt_core`, enforced by composite foreign key constraints `(organization_id, id)` so that cross-organization references are rejected at the relational constraint layer.
* **FR-1.2 (P1, Core — Authoritative Role & Report-Level Permission Enforcement)**:
  * **FR-1.2a**: The server shall enforce the exact actor, role, and resource rules defined in **Table 2.2 (Authoritative Permission Matrix)** across all API routes.
  * **FR-1.2b**: Retrieving report ciphertexts (`GET /api/v1/reports/{id}`) or presigned attachment download URLs shall be permitted exclusively to: (1) the submitting researcher (`HUNTER` matching `report.hunter_id` or `GUEST` matching `guest_token_hash`, receiving Class A and Class B fields only, with Class C columns stripped at the query projection layer), (2) an `ORG_DEFENDER` or `ORG_OWNER` with an active row in `REPORT_RECIPIENT` (`is_active = true`, receiving Class A, Class B, and Class C fields), or (3) an MFA-verified `ORG_OWNER` executing an audited emergency recovery fetch via `POST /api/v1/reports/{id}/recovery-fetch` (`FR-3.8b`).
* **FR-1.3 (P1, Core — Authentication, Password Hashing & Mandatory Owner TOTP MFA)**:
  * **FR-1.3a**: User passwords shall be hashed on the server using **Argon2id** (`m = 65536 KiB [64 MiB], t = 3, p = 4, salt = 16 bytes, tag = 32 bytes`; with **Bcrypt** `cost = 12` supported solely for legacy fixture migration).
  * **FR-1.3b**: Authenticated sessions shall use 256-bit cryptographically random tokens persisted as SHA-256 hashes in the `SESSION` table (`HttpOnly; Secure; SameSite=Lax` cookies). Changing or resetting a password shall immediately delete all active `SESSION` rows for that user.
  * **FR-1.3c (Definite TOTP MFA Enforcement Policy)**: RFC 6238 Time-Based One-Time Password (TOTP) Multi-Factor Authentication (`totp_secret` encrypted at rest via AES-256-GCM) is **mandatory for `ORG_OWNER` enrollment during `/onboarding` before any program can be activated** (and optional/recommended for `ORG_DEFENDER`). Furthermore, the server shall require a verified step-up TOTP challenge (`session.mfa_verified_at >= now() - interval '10 minutes'`, returning HTTP `403 Forbidden: MFA_STEP_UP_REQUIRED` if unenrolled or expired) before executing any privileged owner action: (1) activating a program or rotating `recovery_public_key`, (2) invoking `POST /api/v1/reports/{id}/recovery-fetch` or granting historical access via Master Recovery Key, (3) adding/removing `USER_MEMBERSHIP` or `PROGRAM_DEFENDER` members, (4) transitioning a report to `RISK_ACCEPTED` or recovering `REJECTED_SPAM`, (5) configuring or rotating GitHub Personal Access Tokens, and (6) executing administrative capacity-recovery actions (`DELETE /api/v1/organizations/{id}/reservations/expired` or `PATCH /api/v1/admin/organizations/{id}/quota`) under `READ_ONLY_CAPACITY_LOCK`.
* **FR-1.4 (P1, Core — Guided Onboarding Wizard)**: The platform shall provide a Guided Onboarding Wizard (`/onboarding`) enabling an `ORG_OWNER` to complete active setup tasks—workspace slug registration, mandatory TOTP MFA enrollment (`FR-1.3c`), initialization of the tenant's `organization_audit_heads` row (`last_seq_no = 0`, `FR-8.5b`), DNS TXT challenge generation (`FR-2.5`), asset scope configuration, in-browser Curve25519 key generation, mandatory offline **Organization Master Recovery Key** (`recovery_public_key`) test decryption challenge (`FR-3.6`), and in-browser RFC 9116 `security.txt` cleartext signing (`FR-2.2`)—in **<= 15 minutes of active user interaction time** (excluding external DNS TTL propagation wait times).
* **FR-1.5 (Public Program Intake [P1] & Private Tokenized Programs [P2])**:
  * **FR-1.5a (P1, Core — Public Disclosure Program Discovery & Intake)**: The platform shall serve public vulnerability disclosure programs (`/programs/[slug]`) accessible to registered `HUNTER` accounts and unauthenticated `GUEST` researchers.
  * **FR-1.5b (P2, Secondary — Private Program Invitation Tokens)**: The platform shall support invitation-only private programs (`/programs/[slug]/join?token=...`), persisting only the SHA-256 hash (`token_hash`) of invitation tokens and rejecting uninvited access with HTTP `403 Forbidden`.
* **FR-1.6 (P1, Core — Account-Less Guest Vulnerability Intake, OpenPGP Guest Recovery Package & Atomic Replay-Safe Signatures)**: External researchers shall be able to submit encrypted vulnerability reports without registering an account:
  * **FR-1.6a (Durable Guest Actor Identity)**: At submission, the server assigns an immutable UUIDv4 `guest_actor_id` stored on `REPORT.guest_actor_id` and referenced by all subsequent guest comments, retest attestations, and audit events so rotating bearer tokens never breaks historical attribution.
  * **FR-1.6b (Guest Access Token, Ephemeral Report Keypair & Encrypted Retry Cache)**: The browser generates an ephemeral RFC 9580 v6 Curve25519 keypair (`Ed25519` primary signing key + `X25519` encryption subkey; public key stored in `REPORT.guest_public_key`, 64-hex fingerprint stored in `REPORT.guest_key_fingerprint`, Argon2id-protected private key stored in local `IndexedDB`), and the server issues a 256-bit opaque `access_token`, **persisting only its SHA-256 hash (`guest_token_hash`) on `REPORT` and never persisting the raw `access_token` in plaintext in any database column (`submission_sessions`, `guest_mutation_nonces`) or server log**. Before storing the submission or token-rotation response in `submission_sessions.cached_response_json` (30-minute TTL) or `guest_mutation_nonces.response_body_json` (5-minute TTL), the server encrypts `{ report_id, guest_actor_id, access_token }` to `REPORT.guest_public_key` using `openpgp.encrypt` (`encrypted_guest_credentials_armored`, OpenPGP v6 `PKESK` + `SEIPDv2` AEAD) so that only the holder of the guest's `ephemeral_private_key` can decrypt the token on initial response or idempotent retry (`FR-3.5a`, `TC-GUEST-01b`).
  * **FR-1.6c (Standard OpenPGP v6 Password-Encrypted `.bbt-recovery.json` Guest Recovery Package)**: Upon receiving `encrypted_guest_credentials_armored`, the guest browser decrypts `access_token` in memory using `ephemeral_private_key` and encrypts `{ report_id, guest_actor_id, access_token, armored_private_key }` under the guest's recovery passphrase (or a browser-generated 6-word Diceware passphrase) using `OpenPGP.js v6` (`s2kType = openpgp.enums.s2k.argon2`, `aeadProtect = true`) as a standard **RFC 9580 OpenPGP v6 symmetric password-encrypted message (`SYMENC` + `SEIPDv2` AEAD)**, downloading `.bbt-recovery.json` (`{ version: 1, format: "openpgp-symenc-seipdv2", report_id, guest_actor_id, key_fingerprint, encrypted_recovery_bundle }`). Possessing `.bbt-recovery.json` without the passphrase reveals **zero bearer credentials**, and any modification to the ciphertext or inner `report_id`/`guest_actor_id` is rejected by OpenPGP SEIPDv2 authentication tag verification. If a guest clears `IndexedDB` and loses both their passphrase and `.bbt-recovery.json`, guest session access cannot be recovered by the server.
  * **FR-1.6d (URI Fragment Scrubbing & Telemetry Sanitization)**: Immediate post-submission tracking URLs use a client-side URI fragment (`/report/track/BBT-RPT-XXXX#token=<access_token>`) which is never sent in HTTP request lines or `Referer` headers and is scrubbed on load via `window.history.replaceState(null, '', window.location.pathname)`. Error telemetry hooks strip all URI fragments and authorization headers.
  * **FR-1.6e (Local-Only Browser Restoration & Dropped-Response Safe Signature-Only Token Rotation)**:
    1. Selecting `.bbt-recovery.json` on `/report/restore` reads and decrypts `encrypted_recovery_bundle` strictly in browser memory via `FileReader` and `openpgp.decrypt({ message, passwords: [passphrase] })`; the file is **never uploaded to the backend server**.
    2. To rotate a suspected/exposed `access_token` (`POST /api/v1/reports/{id}/guest-token/rotate`), the request invokes the dedicated signature-only entrypoints (`bbt_core.fn_guest_get_rotation_context` and `bbt_core.fn_guest_rotate_token_by_sig`, `FR-8.2c`) and authenticates using an **OpenPGP v6 detached signature (`X-Guest-Signature`)** produced by the guest's `ephemeral_private_key` (`REPORT.guest_public_key`) over the canonical rotation payload (`action = "ROTATE_GUEST_TOKEN"`, `nonce`, `issued_at`, `expires_at`)—**without requiring any bearer `access_token`**. The server encrypts the newly generated `{ report_id, guest_actor_id, access_token }` to `REPORT.guest_public_key` (`encrypted_guest_credentials_armored`) and caches only that ciphertext in `guest_mutation_nonces.response_body_json` (5-minute TTL). If the HTTP response is lost in transit after the server rotates `guest_token_hash`, the guest's browser either retries with the same `nonce` (receiving the cached `encrypted_guest_credentials_armored` and decrypting it locally with `ephemeral_private_key`) or signs a fresh rotation request with a new `nonce`, guaranteeing that a dropped rotation response never locks out the guest nor persists a raw token on the server.
  * **FR-1.6f (Canonical RFC 8785 JCS Guest Signature Proof-of-Possession, Canonical Lock Order & Shared-Transaction Nonce Idempotency)**:
    1. Every guest mutation—posting a comment (`POST_COMMENT`), withdrawing a report (`WITHDRAW_REPORT`), submitting a retest outcome (`VERIFIED_RESEARCHER` or `RETEST_FAILED`), or rotating a guest token (`ROTATE_GUEST_TOKEN`)—requires a detached **OpenPGP v6 Ed25519 signature (`X-Guest-Signature`)** created via `openpgp.sign({ message, signingKeys: [guestPrivateKey], detached: true })` over the **RFC 8785 JSON Canonicalization Scheme (JCS)** byte serialization of:
       `{ "protocol": "bbt-guest-pop-v1", "report_id": "<uuid>", "state_version": <int>, "action": "<ENUM>", "remediation_record_id": "<uuid|null>", "payload_sha256": "<64-hex>", "nonce": "<32-hex-128bit>", "issued_at": "<ISO8601>", "expires_at": "<ISO8601 (+300s)>" }`.
    2. For `VERIFIED_RESEARCHER` and `RETEST_FAILED`, `remediation_record_id` is mandatory and must match the report's active `remediation_record_id`.
    3. **Shared Atomic Transaction Boundary & Canonical Lock Order (`organizations -> reports -> organization_audit_heads`)**: After the Node.js handler verifies the OpenPGP detached signature against `REPORT.guest_public_key` and asserts `expires_at >= now()` (max 5-minute TTL, `<= 60s` clock skew tolerance), the database transaction first resolves `v_org_id` via a non-locking lookup on `bbt_core.reports` and then acquires row locks strictly in the universal canonical lock order (`FR-7.1b`): **(i) locks `bbt_core.organizations WHERE id = v_org_id FOR UPDATE`, (ii) locks `bbt_core.reports WHERE id = p_report_id FOR UPDATE`**, (iii) checks `guest_mutation_nonces` (`PRIMARY KEY (report_id, nonce)`), and (iv) if `(report_id, nonce)` does not exist, executes the domain mutation (inserting the comment, updating report state, or rotating `guest_token_hash`), locks `bbt_core.organization_audit_heads FOR UPDATE` to append the `audit_events` row, and inserts `(report_id, nonce, action, request_sha256, response_status, response_body_json, expires_at)` into `guest_mutation_nonces` (5-minute TTL, purged hourly by `fn_cron_evaluate_overdue_deadlines`) in the **same commit**. Locking `organizations` before `reports` ensures that the byte-accounting trigger on `organizations` never inverts lock order against concurrent submission or triage transactions.
    4. **Idempotent Retry vs. Replay Rejection**: If a request with an existing `(report_id, nonce)` arrives before `expires_at` with the exact same `action` and `request_sha256`, the transaction returns the cached `response_body_json` (containing only ciphertext `encrypted_guest_credentials_armored` for rotation requests) without creating duplicate messages or re-executing the mutation. If `(report_id, nonce)` is reused with any modified field, or if `expires_at < now()`, the server rejects the request with HTTP `409 Conflict` / `401 Unauthorized`.

### 3.2 RFC 9116 Policy Discovery & Safe Harbor Engine (`FR-2` — MVP Feature 1)

* **FR-2.1 (P1, Core — RFC 9116 Manifest Generation)**: The platform shall generate an RFC 9116 compliant text manifest at `/api/v1/programs/[slug]/security.txt` containing the standard RFC 9116 directives: `Contact` (pointing to the program's encrypted submission URI), `Expires` (ISO 8601 timestamp capped at `<= 365 days` from signing, with automated dashboard warnings 30 days before expiry), `Encryption` (URI to the program's OpenPGP v6 public keyring), `Policy` (URI to the hosted Safe Harbor & Scope policy page), `Acknowledgments`, `Preferred-Languages`, and `Canonical`.
* **FR-2.2 (P1, Core — In-Browser OpenPGP Cleartext Signing)**: The `security.txt` manifest shall be **cleartext-signed in the client browser** (`-----BEGIN PGP SIGNED MESSAGE-----`) using the `ORG_OWNER`'s private Ed25519 signing key without transmitting the private key to the server.
* **FR-2.3 (P1, Core — Signature & Fingerprint Verification)**: The platform shall verify cleartext-signed `security.txt` manifests against the organization's advertised 64-character SHA-256 public key fingerprint, allowing researchers to cross-verify the platform's encryption key against `https://[org-domain]/.well-known/security.txt`.
* **FR-2.4 (P1, Core — Structured Asset Scope & Hosted Safe Harbor Terms)**: Recognizing per RFC 9116 Section 1 that `security.txt` is a discovery manifest rather than a standalone legal contract, the platform shall host the human- and machine-readable **Safe Harbor & Scope Policy** at the URI referenced by the `Policy:` directive (`/programs/[slug]`), defining structured **In-Scope (`IN_SCOPE`)** and **Out-of-Scope (`OUT_OF_SCOPE`)** asset tables and good-faith Safe Harbor authorization clauses adapted from Disclose.io Core terms.
* **FR-2.5 (P1, Core — DNS TXT Domain Ownership Verification)**: Prior to marking an organization domain as `DOMAIN_VERIFIED` for public discovery, the backend shall verify domain ownership via Node.js `dns.promises.resolveTxt('_bbt-challenge.<domain>')` matching the tenant's unique verification token (sandbox evaluation workspaces may operate in `[SANDBOX_UNVERIFIED_DOMAIN]` mode during local grading without blocking P1 onboarding).

### 3.3 Client-Side OpenPGP v6 Pipeline & Key Lifecycle Management (`FR-3` — MVP Feature 2)

* **FR-3.1 (P1, Core — Pinned RFC 9580 v6 Curve25519 Key Generation)**: The client browser shall generate OpenPGP keypairs pinned strictly to **RFC 9580 Version 6 Curve25519 (`Ed25519` primary signing key + `X25519` encryption subkey)** by enforcing `openpgp.config.v6Keys = true`. Key fingerprints shall be 64-character lowercase hexadecimal SHA-256 strings stored in `USER_KEY (key_id, user_id, key_fingerprint, armored_public_key, status)`. Bare keypair generation in `< 50 ms` is designated as a provisional benchmark target on reference hardware.
* **FR-3.2 (P1, Core — Explicit Argon2id S2K Selection & `IndexedDB` Keystore)**: Private keys in browser `IndexedDB` (zero `localStorage` usage) shall be encrypted using OpenPGP **Argon2id S2K** by setting **both `openpgp.config.s2kType = openpgp.enums.s2k.argon2` and `openpgp.config.s2kArgon2Params = { passes: 3, parallelism: 4, memoryExponent: 16 }`** (`65,536 KiB = 64 MiB`, introducing an intentional, estimated cryptographic delay of `~200–400 ms` during passphrase unlock) with `openpgp.config.aeadProtect = true`. Automated unit tests (`TC-CRYPTO-02`) shall parse the serialized secret-key packet bytes to verify that S2K specifier `0x04` (Argon2id) and `memoryExponent = 16` are present in the emitted key material.
* **FR-3.3 (P1, Core — Multi-Recipient Encryption, Key-Versioned `REPORT_RECIPIENT` & Stale-Recipient Guards)**:
  * **FR-3.3a (Initial Submission Recipients & `recipient_set_version`)**: On initial report submission (`POST /api/v1/reports`), all Class B fields (and `K_file` attachment session keys per `FR-3.5b`) shall be encrypted for the **Authoritative Class B Recipient Set**: (1) all active `PROGRAM_DEFENDER` key versions (`key_id`, up to 10 defenders, which the server snapshots into `REPORT_RECIPIENT`), (2) the organization's active `recovery_public_key` (`recovery_key_fingerprint` recorded on the ciphertext), and (3) the submitter's active public encryption key (`USER_KEY` `submitter_key_id` for registered `HUNTER`s or `guest_public_key` for `GUEST`s). If the submitted `PROGRAM.recipient_set_version` is stale, the server rejects the submission with HTTP `409 Conflict` and returns the updated keyring.
  * **FR-3.3b (Subsequent Writes on Existing Reports & `report_recipient_version`)**: Every subsequent encrypted write on an existing report (comments, internal notes, CVSS explanations/notes, remediation notes, configuration snapshots, retest evidence, or attachments) shall generate a **fresh random 256-bit OpenPGP session key**, encrypt strictly for the report's active `REPORT_RECIPIENT` key records (`is_active = true` and `USER_KEY.status = 'ACTIVE'`) plus `PROGRAM.recovery_public_key` (**plus the submitter's active key `submitter_key_id` / `guest_public_key` for all Class B text and attachment objects**), and submit the report's current `report_recipient_version`. If `REPORT.report_recipient_version` changed concurrently (e.g., a defender was removed from the program/organization, a key was revoked, or the researcher replaced their key), the server rejects the write with HTTP `409 Conflict` and returns the updated recipient keyring and `report_recipient_version`.
* **FR-3.4 (P1, Core — Encrypted Title & Coarse `operational_label` Enum)**: The specific vulnerability title shall be encrypted as `title_ciphertext` (Class B), while the submitter selects a coarse Class A `operational_label` enum (`AUTHENTICATION_BYPASS`, `INJECTION_VULNERABILITY`, `INFORMATION_DISCLOSURE`, `CROSS_SITE_SCRIPTING`, `ACCESS_CONTROL_ISSUE`, `DENIAL_OF_SERVICE`, `CRYPTOGRAPHIC_CONFIGURATION`, or `OTHER`) for queue filtering and non-leaking notifications.
* **FR-3.5 (P1, Core — Atomic Single-Use Submission Sessions, Encrypted Guest Cache, OpenPGP Binary Attachment Encryption & Safe Downloads)**:
  * **FR-3.5a (Single Turnstile Validation -> Atomic Single-Use `submission_sessions`, Encrypted Guest Retry Cache & Upload Reservations)**:
    1. To avoid re-validating single-use Cloudflare Turnstile tokens across presigning and final submission, the client validates Turnstile once via `POST /api/v1/submission-sessions` (executed outside DB transactions) to create a row in `bbt_core.submission_sessions (session_id, program_id, organization_id, status = 'OPEN', request_payload_sha256, created_report_id, cached_response_json, expires_at = now() + interval '30 minutes')`, allowing up to **`3` attachments per report**, each **`<= 25 MiB` (`26,214,400 bytes`)** encrypted size, and **`<= 50 MiB` (`52,428,800 bytes`)** total encrypted report size.
    2. Calling `POST /api/uploads/presign` with `(submission_session_token, exact_ciphertext_bytes, ciphertext_sha256)` verifies `submission_sessions.status == 'OPEN'` and creates a 15-minute `upload_reservations` record bound to a server-generated UUID `r2_object_key`, returning a presigned R2 `PUT` URL locked to `Content-Length = exact_ciphertext_bytes` and `If-None-Match: *`.
    3. **Atomic Consumption, Encrypted Guest Credentials & Idempotent Retry on `POST /api/v1/reports`**: Whether a report submission includes attachments or **zero attachments**, the final `POST /api/v1/reports` transaction follows the canonical lock order (`2. organizations -> 3. programs -> 4. submission_sessions -> 5. reports -> 6. organization_audit_heads`) and locks `SELECT * FROM bbt_core.submission_sessions WHERE session_id = :sid FOR UPDATE`. If `status == 'OPEN'` and `expires_at > now()`, the server transitions `submission_sessions.status = 'CONSUMED'`, records `request_payload_sha256` and `created_report_id`, binds any `upload_reservations`, and inserts the report in the **same atomic commit**. **Guest Credential Protection in `cached_response_json` (`FR-1.6b`)**: For guest submissions, the server encrypts `{ report_id, guest_actor_id, access_token }` to `REPORT.guest_public_key` (`encrypted_guest_credentials_armored`) and persists **only `{ report_id, guest_actor_id, encrypted_guest_credentials_armored }` (never a plaintext `access_token`)** in `submission_sessions.cached_response_json` (retained for at most **30 minutes** until `expires_at` and purged by the hourly cron job in `Section 2.6`). If a retry arrives for a `CONSUMED` session before `expires_at` with the **exact same `request_payload_sha256`**, the server returns the cached `201 Created` `cached_response_json` idempotently so the guest browser decrypts `encrypted_guest_credentials_armored` with `ephemeral_private_key` without creating a duplicate report; if `request_payload_sha256` differs, the server rejects the reuse with HTTP `409 Conflict: SUBMISSION_SESSION_ALREADY_CONSUMED`.
  * **FR-3.5b (Standard OpenPGP v6 SEIPDv2 Binary Attachment Encryption & Authoritative Class B `K_file` Wrapping)**: The browser generates a random 256-bit OpenPGP session key (`K_file = await openpgp.generateSessionKey(...)`), encrypts the attachment binary (including filename and MIME metadata inside the literal packet) as a standard **OpenPGP v6 SEIPDv2 AEAD binary message (`openpgp.encrypt({ message: await openpgp.createMessage({ binary }), sessionKey: K_file, format: 'binary', config: { aeadProtect: true } })`)**, computes its SHA-256 hash (`ciphertext_sha256`), and uploads the ciphertext once to Cloudflare R2. Using the **exact same Authoritative Class B Recipient Rule (`Table 2.1`, `FR-3.3`)**, the session key `K_file` and `ciphertext_sha256` are wrapped via `openpgp.encryptSessionKey` into `encrypted_file_key_packet` for **all active `REPORT_RECIPIENT` keys (`key_id`) + `PROGRAM.recovery_public_key` + the submitter's active public key (`submitter_key_id` or `guest_public_key`)**. If `recipient_set_version` or `report_recipient_version` is stale (`409 Conflict`), the browser re-wraps `K_file` for the updated Class B recipient set without re-uploading the R2 binary blob.
  * **FR-3.5c (Safe Decrypted Attachment Handling)**: After downloading from R2, the browser verifies `ciphertext_sha256` before decrypting with `K_file`. Decrypted attachments are never rendered inline in the DOM or inside an `<iframe>`; downloads are triggered via isolated `Blob` object URLs with forced `download` attributes, `Content-Disposition: attachment`, and `X-Content-Type-Options: nosniff`.
* **FR-3.6 (P1, Core — Offline Organization Master Recovery Key & Best-Effort Memory Hygiene)**: During onboarding, the browser generates an offline RFC 9580 v6 Curve25519 **Organization Master Recovery Keypair** (`recovery_public_key` and `recovery_key_fingerprint` stored on `PROGRAM`; private key exported offline as a standard OpenPGP v6 armored secret key encrypted with Argon2id S2K via `s2kType = openpgp.enums.s2k.argon2`). Program activation requires passing an in-browser test decryption challenge using the exported file. Upon key lock or logout, temporary `Uint8Array` buffers are zeroized (`fill(0)`), ephemeral keys are deleted from `IndexedDB` when requested, and all in-memory JavaScript object references are immediately nullified as a best-effort defense-in-depth measure.
* **FR-3.7 (P1, Core — Standardized Registered User Personal Key Backup `.bbt-user-keys.json`)**: Registered `HUNTER`, `ORG_DEFENDER`, and `ORG_OWNER` users shall be able to export and import a **Personal Key Backup Bundle (`.bbt-user-keys.json`)** on `/settings/keys` (`SCR-10`, processed strictly in local browser memory via `FileReader` with zero network upload). The file contains `{ version: 1, format: "openpgp-v6-secret-key", user_id, key_id, key_fingerprint, created_at, armored_private_key, armored_public_key }` where `armored_private_key` is the standard RFC 9580 OpenPGP v6 armored secret key protected natively by OpenPGP's Argon2id S2K (`s2kType = openpgp.enums.s2k.argon2`, `aeadProtect = true`).
* **FR-3.8 (P1, Core — Three-Tier Offboarding/Revocation Scope, Separated Researcher vs. Defender Historical Re-Wrapping & Owner Recovery)**:
  * **FR-3.8a (Explicit Three-Tier Scope: Program Removal vs. Organization Removal vs. Global Key Revocation & Deterministic Multi-Row Lock Order)**:
    All three revocation/removal operations acquire row locks strictly in the universal canonical lock order (`2. organizations ORDER BY id ASC FOR UPDATE -> 3. programs ORDER BY id ASC FOR UPDATE -> 5. reports ORDER BY id ASC FOR UPDATE -> 6. organization_audit_heads ORDER BY organization_id ASC FOR UPDATE`, `FR-7.1b`):
    1. *Program-Level Defender Removal (`DELETE /api/v1/programs/{program_id}/defenders/{user_id}`)*: When `ORG_OWNER` (with step-up MFA) removes a defender from a single program (`program_id`), the server atomically sets `is_active = false` on their `PROGRAM_DEFENDER` row for `program_id` and on all `REPORT_RECIPIENT` rows **strictly for reports belonging to `program_id`**, incrementing `program_id.recipient_set_version` and `REPORT.report_recipient_version` on `program_id`'s reports—**while preserving the defender's authorized `PROGRAM_DEFENDER` and `REPORT_RECIPIENT` access on Program B in the same organization**.
    2. *Organization-Level Member Offboarding (`DELETE /api/v1/organizations/{org_id}/members/{user_id}`)*: When `ORG_OWNER` (with step-up MFA) removes a member from `USER_MEMBERSHIP` in `org_id`, the server atomically deactivates their `USER_MEMBERSHIP` in `org_id`, sets `is_active = false` on all `PROGRAM_DEFENDER` and `REPORT_RECIPIENT` rows across all programs and reports within `org_id`, increments `recipient_set_version` and `report_recipient_version` across `org_id`, and revokes their `org_id` session context—**without affecting that user's `USER_KEY` or their memberships/access in Organization B**.
    3. *Global Key Compromise / Lost Key Revocation (`POST /api/v1/keys/{key_id}/revoke`)*: When a user marks a `USER_KEY (key_id)` as `REVOKED` (compromised or permanently lost), the server locks all affected `organizations`, `programs`, and `reports` in `ORDER BY id ASC FOR UPDATE` order, sets `USER_KEY.status = 'REVOKED'`, deactivates all `PROGRAM_DEFENDER` and `REPORT_RECIPIENT` rows referencing `key_id` across every organization and program, marks any `REPORT.submitter_key_id == key_id` as requiring replacement, and increments `recipient_set_version` and `report_recipient_version` on all affected programs and reports.
  * **FR-3.8b (Separated Defender vs. Researcher Historical Re-Wrapping, Complete Object Inventory & `SEIPDv2` Hash Coexistence)**:
    1. *Path 1 — Defender Historical Access Grant (`POST /api/v1/reports/{id}/grant-defender-access`, `CLASS_B_AND_C`)*: Used when granting an authorized `ORG_DEFENDER`'s active `USER_KEY (key_id)` access to an existing report (or restoring a defender after key loss). Re-wraps **100% of Class B and Class C encrypted objects on `report_id`**:
       - (i) `REPORT` root ciphertexts (`title_ciphertext`, `encrypted_payload`, `cvss_explanation_ciphertext`, `cvss_internal_notes_ciphertext`, `rejection_reason_ciphertext`, `risk_rationale_ciphertext`, `audit_justification_ciphertext`),
       - (ii) **all `CVSS_ASSESSMENT_HISTORY` rows** (`cvss_explanation_ciphertext` [Class B] and `cvss_internal_notes_ciphertext` [Class C]),
       - (iii) all `DISCUSSION_MESSAGE` rows in **both** `RESEARCHER_ORG` (Class B) and `REVIEWER_INTERNAL` (Class C) lanes,
       - (iv) all `REMEDIATION_RECORD` (`remediation_notes_ciphertext`, `config_artifact_ciphertext`) and `RETEST_EVIDENCE` (`verification_notes_ciphertext`) rows, and
       - (v) all `ATTACHMENT.encrypted_file_key_packet` entries.
       Upon commit, activates `(report_id, user_id, key_id)` in `REPORT_RECIPIENT`, increments `report_recipient_version`, and logs `HISTORICAL_ACCESS_GRANTED`.
    2. *Path 2 — Registered Researcher Class B Key Replacement Re-Wrap (`POST /api/v1/reports/{id}/rewrap-researcher-key`, `CLASS_B_ONLY`)*: Used when the submitting registered researcher (`HUNTER` matching `report.hunter_id`) loses their device without `.bbt-user-keys.json` and registers a replacement `USER_KEY (key_id_new)`. An authorized defender in `REPORT_RECIPIENT` (or MFA-verified `ORG_OWNER` via Master Recovery Key) re-wraps session keys for `key_id_new` **strictly across Class B objects on `report_id`**:
       - (i) `REPORT` Class B columns only (`title_ciphertext`, `encrypted_payload`, `cvss_explanation_ciphertext`, `rejection_reason_ciphertext`),
       - (ii) **`CVSS_ASSESSMENT_HISTORY.cvss_explanation_ciphertext` (Class B) only** (`cvss_internal_notes_ciphertext` is strictly excluded),
       - (iii) `DISCUSSION_MESSAGE` rows where **`lane = 'RESEARCHER_ORG'` only** (`REVIEWER_INTERNAL` rows are strictly excluded),
       - (iv) `REMEDIATION_RECORD` (`remediation_notes_ciphertext`, `config_artifact_ciphertext`), `RETEST_EVIDENCE` (`verification_notes_ciphertext`), and `ATTACHMENT.encrypted_file_key_packet`.
       Upon commit, the server updates `REPORT.submitter_key_id = key_id_new`, increments `REPORT.report_recipient_version` (so all subsequent Class B writes encrypt to `key_id_new`), **never adds the researcher to `REPORT_RECIPIENT`**, and logs `RESEARCHER_KEY_REWRAPPED`.
    3. *Coexistence of Key-Envelope (`PKESK`) Appends with Immutable Audit Hashes (`seipdv2_body_sha256`)*: In RFC 9580 OpenPGP messages, recipient `PKESK` packets (Tag 1) precede the immutable `SEIPDv2` AEAD ciphertext body packet (Tag 18). Every encrypted field/row stores `(envelope_version INT, seipdv2_body_sha256 CHAR(64), full_message_sha256 CHAR(64))`, and historical `audit_events` commitments bind to **`seipdv2_body_sha256`**. Appending a new `PKESK` packet during Path 1 or Path 2 increments `envelope_version` and updates `full_message_sha256` (recorded in the new `HISTORICAL_ACCESS_GRANTED` or `RESEARCHER_KEY_REWRAPPED` audit event) while **`seipdv2_body_sha256` remains immutable**, guaranteeing that key re-wrapping never invalidates prior audit commitments.
    4. *Exact Object ID, Envelope Version Manifest Validation & Canonical Lock Order (`organizations -> reports -> organization_audit_heads`)*: Both `grant-defender-access` and `rewrap-researcher-key` require submitting `state_version` and an explicit manifest array `objects: [{ object_type, object_id, field_name, prev_envelope_version, seipdv2_body_sha256, appended_pkesk_b64 }]`. Inside a single database transaction that locks **`2. organizations FOR UPDATE` -> `5. reports FOR UPDATE` -> `6. organization_audit_heads FOR UPDATE`** (`FR-7.1b`), the server queries the exact authoritative set of `(object_type, object_id, field_name, envelope_version, seipdv2_body_sha256)` required for that path (`CLASS_B_AND_C` vs. `CLASS_B_ONLY`); if any required object ID/field is missing, extra, has a stale `prev_envelope_version`, or modifies `seipdv2_body_sha256`, the transaction rolls back with HTTP `409 Conflict`.
    5. *Audited Owner Recovery Fetch (`POST /api/v1/reports/{id}/recovery-fetch`)*: When all defenders have lost their local browser keystores, the MFA-authenticated `ORG_OWNER` calls `POST /api/v1/reports/{id}/recovery-fetch` (locking `organizations -> reports -> organization_audit_heads`), which atomically appends `MASTER_RECOVERY_FETCH_INITIATED` to `audit_events` before returning the report's ciphertext bundle for in-browser decryption with the offline Master Recovery Key.
  * **FR-3.8c (Master Recovery Key Rotation & Historical Key Retention)**: `ORG_OWNER` (authenticated via step-up TOTP MFA) may rotate `PROGRAM.recovery_public_key` by completing a new offline key generation and decryption challenge, incrementing `PROGRAM.recipient_set_version` and `REPORT.report_recipient_version`. Each ciphertext stores the `recovery_key_fingerprint` active when it was created; rotating `recovery_public_key` applies to **future encrypted writes only**, so organizations must retain prior offline Master Recovery Key files (or execute an in-browser batch re-wrap from the old recovery key to the new recovery key).

### 3.4 Deterministic CVSS 3.1 Base Scoring Engine (`FR-4` — MVP Feature 3)

* **FR-4.1 (P1, Core — Deterministic FIRST.org CVSS v3.1 Mathematical Engine & Server Recalculation)**: Computing the **CVSS v3.1 Base Score** (`0.0` to `10.0`) from a selected vector shall be 100% deterministic. Both client and server share a pure, zero-dependency TypeScript engine using the official FIRST.org exploitability coefficient **`8.22`** and FIRST.org Appendix A integer-scaled `RoundUp` ceiling function (`Math.ceil(Math.round(val * 100000) / 10000) / 10` to eliminate IEEE 754 floating-point drift). The backend server **always recalculates `cvss_score` and Qualitative Severity Rating authoritatively from the canonicalized vector string** (`CVSS_TEST_FIXTURES.md`: **100% exact numeric reference parity across 45 FIRST.org and NIST NVD test fixtures**, plus **100% mathematical invariant compliance across all 2,592 valid Base metric combinations**).
* **FR-4.2 (P1, Core — 8 Base Metrics & Scope-Changed Weight Adjustment)**: The engine shall evaluate Attack Vector (`AV:N/A/L/P`), Attack Complexity (`AC:L/H`), Privileges Required (`PR:N/L/H`, applying official Scope-Changed weights `PR:L = 0.68`, `PR:H = 0.50` when `S:C` vs. `0.62` and `0.27` when `S:U`), User Interaction (`UI:N/R`), Scope (`S:U/C`), Confidentiality (`C:N/L/H`), Integrity (`I:N/L/H`), and Availability (`A:N/L/H`).
* **FR-4.3 (P1, Core — Order-Insensitive Base Vector Parser, Canonical Serializer & Temporal/Environmental Rejection)**:
  * Per the FIRST.org CVSS v3.1 Specification, the vector parser shall **accept the 8 required Base metrics (`AV, AC, PR, UI, S, C, I, A`) in any input order**, and the serializer shall output accepted vectors in **canonical FIRST.org order** (`CVSS:3.1/AV:_/AC:_/PR:_/UI:_/S:_/C:_/I:_/A:_`).
  * The parser shall reject vectors with missing Base metrics, duplicate metric keys, invalid metric values, or malformed headers (`422 Unprocessable Entity`), and shall explicitly reject optional Temporal (`E, RL, RC`) or Environmental (`CR, IR, AR, MAV, MAC, MPR, MUI, MS, MC, MI, MA`) metrics with a clear error (`Base metrics only supported in MVP`).
  * Numeric scores map deterministically to Qualitative Severity Ratings (`None: 0.0`, `Low: 0.1–3.9`, `Medium: 4.0–6.9`, `High: 7.0–8.9`, `Critical: 9.0–10.0`).
* **FR-4.4 (P1, Core — Researcher-Visible Score Explanation, Optional Internal Notes & Assessment History)**:
  * The `REPORT` record stores `cvss_suggested` (submitted by the researcher) and official `cvss_vector` / `cvss_score` (assigned by the defender as Class A metadata).
  * Whenever a defender assigns or modifies the official CVSS assessment (especially when differing from `cvss_suggested`), the defender **must** provide a **Researcher-Visible CVSS Explanation (`cvss_explanation_ciphertext`, Class B Shared Content)** encrypted for the submitter, `REPORT_RECIPIENT`, and `recovery_public_key` so the researcher understands why each metric was chosen, and **may** optionally record confidential architectural details in **Internal CVSS Notes (`cvss_internal_notes_ciphertext`, Class C Internal Content)** encrypted strictly for `REPORT_RECIPIENT` and `recovery_public_key`.
  * Every assessment is appended to `CVSS_ASSESSMENT_HISTORY (assessment_id, report_id, actor_id, cvss_vector, cvss_score, cvss_explanation_ciphertext, cvss_internal_notes_ciphertext, envelope_version, seipdv2_body_sha256, created_at)` and bound into `audit_events`.

### 3.5 Confidential Triage, Dual-Lane Threading & SLA Timers (`FR-5` — MVP Feature 4)

* **FR-5.1 (P1, Core — In-Browser Decryption & Triage Desk)**: Authorized defenders in `REPORT_RECIPIENT` shall unlock their private X25519 subkey in-browser via Argon2id S2K to decrypt Class B and Class C ciphertexts on `/dashboard/reports/[id]`.
* **FR-5.2 (P1, Core — Dual-Lane Report-Scoped Encrypted Threading with `report_recipient_version`)**: The triage desk shall enforce two cryptographically isolated message lanes checked against `REPORT.report_recipient_version`:
  * **Lane 1 (`RESEARCHER_ORG` — Class B)**: Fresh session key encrypted for Submitter Active Key (`submitter_key_id` or `guest_public_key`) + Active `REPORT_RECIPIENT` Keys + `recovery_public_key` (counted against the `20 MiB` intake pool [including the `1.0 MiB` active-report researcher response sub-reserve] when posted by the researcher, or the `6 MiB` reserve when posted by a defender).
  * **Lane 2 (`REVIEWER_INTERNAL` — Class C)**: Fresh session key encrypted strictly for Active `REPORT_RECIPIENT` Keys + `recovery_public_key` (submitter key excluded and stripped from researcher API responses; counted against the `6 MiB` security/triage reserve).
* **FR-5.3 (P1, Core — Strict Class A Metadata-Only Notifications via Transactional Outbox)**: Outbound email notifications (Resend/Postmark) and webhook alerts shall be enqueued in a transactional `notification_outbox` table inside the same database commit as the triggering `audit_events` row and shall contain **strictly Class A notification fields** (`report_id`, `operational_label`, `from_state -> to_state`, `timestamp`, portal URL, and the signed Audit Checkpoint Receipt containing `organization_slug` and `org_commitment`), containing **zero bytes** of Class B or Class C content.
* **FR-5.4 (P1, Core — 3-Phase Claim-Lease Hourly Authenticated SLA, Inactivity, Bounded Purge & R2 Cleanup Scheduler with Per-Batch Finalization & DB Timeouts)**:
  * Triggered hourly (`0 * * * *`) via an authenticated GitHub Actions scheduled workflow (`POST /api/cron/lifecycle-evaluate` signed with `X-Cron-Timestamp` and `X-Cron-Signature` per `Section 2.6`), the scheduler loops up to **`3` sequential `Phase 1 -> Phase 2 -> Phase 3` batches per invocation (`<= 30` R2 objects, `<= 150` deadlines, `<= 600` purges, starting a batch only when `elapsed_ms <= 8,000 ms`)** so external R2 HTTP calls never run inside a PostgreSQL transaction, every batch finalizes immediately after its own Phase 2 (with `11,000 ms .. 15,000 ms` [`4,000 ms`] reserved as remaining invocation headroom for the final batch's Phase 3), and crashed or timed-out workers never leave reservations permanently stuck:
    1. **Phase 1 — Short DB Transaction #1 (`bbt_core.fn_cron_evaluate_overdue_deadlines(now(), p_deadline_limit => 50, p_r2_claim_limit => 10, p_purge_limit => 200)` — Target `<= 400 ms`, Enforced `connectionTimeoutMillis = 1,000 ms`, `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)**: Acquires PostgreSQL transaction advisory lock `pg_try_advisory_xact_lock(889001)` (ignoring duplicate concurrent triggers), purges up to **`p_purge_limit => 200` expired `submission_sessions` rows** and up to **`p_purge_limit => 200` expired `guest_mutation_nonces` rows** (`WHERE expires_at < now() ORDER BY expires_at ASC LIMIT 200 FOR UPDATE SKIP LOCKED`), evaluates up to **`p_deadline_limit => 50` overdue Class A SLA targets** (`Critical: 48h triage / 14d fix`, `High: 72h triage / 30d fix`, `Medium: 7d triage / 90d fix`, `Low: 14d triage / 180d fix`) and overdue `NEED_MORE_INFO` reports (`info_timeout_due <= now() AND capacity_deadline_paused = false -> CLOSED_INCOMPLETE`, `FR-7.5`), and claims up to **`p_r2_claim_limit => 10` expired or lease-timed-out `upload_reservations` rows** (`WHERE (status IN ('RESERVED', 'DELETE_FAILED') AND expires_at <= now()) OR (status = 'DELETING' AND claim_expires_at <= now()) ORDER BY reservation_id ASC LIMIT 10 FOR UPDATE SKIP LOCKED`), atomically setting **`status = 'DELETING'`, `claim_id = gen_random_uuid()`, and `claim_expires_at = now() + interval '2 minutes'`** and returning `(reservation_id, claim_id, organization_id, r2_object_key, exact_ciphertext_bytes)` plus `has_more_deadline_backlog BOOLEAN`, `has_more_r2_backlog BOOLEAN`, `has_more_purge_backlog BOOLEAN`, and the unified **`has_more_backlog = (has_more_deadline_backlog OR has_more_r2_backlog OR has_more_purge_backlog)`**.
    2. **Phase 2 — Node.js Cloudflare R2 Deletion Outside DB Transactions with `1,000 ms` Per-Request Timeout & `11,000 ms` Hard Invocation Cutoff (`<= 2.2s` per 10-object batch)**: Calls R2 `DeleteObjectCommand` for each of the `<= 10` claimed `r2_object_key` entries at **concurrency `5` (`<= 2` waves)** with `AbortSignal.any([AbortSignal.timeout(1000), AbortSignal.timeout(Math.max(0, 11000 - elapsed_ms))])` (`204 No Content` and `404 Not Found` both count as confirmed physical deletion; any request exceeding `1,000 ms` or aborted/unstarted at `t == 11,000 ms` is marked for `'DELETE_FAILED'`).
    3. **Phase 3 — Immediate Per-Batch DB Transaction #2 (`bbt_core.fn_cron_finalize_r2_deletions` — Target `<= 400 ms`, Enforced `connectionTimeoutMillis = 1,000 ms`, `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)**: Executed immediately after the batch's Phase 2 completes (with `11,000 ms .. 15,000 ms` [`4,000 ms`] available as reserved invocation headroom if the final batch's Phase 2 runs until `11,000 ms`), locks `1. cluster_storage_state -> 2. organizations (ORDER BY id ASC)`, matches **`WHERE reservation_id = :res_id AND status = 'DELETING' AND claim_id = :claim_id`**, and transitions confirmed rows from `'DELETING'` to `'DELETED'` (`FR-8.4`), crediting back `exact_ciphertext_bytes` **strictly when `status = 'DELETING' AND claim_id = :claim_id` transitions to `'DELETED'` (`ROW_COUNT == 1`)** (and setting `status = 'DELETE_FAILED', claim_id = NULL, claim_expires_at = NULL` without crediting bytes for any failed, timed-out, or cutoff-aborted R2 request, setting `has_more_r2_backlog = true` and `has_more_backlog = true`). If Phase 3 cannot acquire a connection, times out (`55P03` / `57014`), or fails to commit before the invocation deadline, the transaction rolls back, the handler does not report successful finalization, sets `has_more_r2_backlog = true` (`has_more_backlog = true`), and leaves the rows in `'DELETING'` for lease-expiry reclaim (`claim_expires_at <= now()`) on a subsequent run. Whenever **`has_more_backlog == true`** remains after `<= 3` batches, `lifecycle-cron.yml` immediately triggers a follow-up `workflow_dispatch` continuation (up to `10` chained runs) until all deadline, purge, and R2 backlogs are drained.
* **FR-5.5 (Privacy-Preserving Duplicate Linking & Deterministic Multi-Row Lock Order [P1 Core Binding / P2 UI Helper])**:
  * **FR-5.5a (P1, Core — Canonical Duplicate Binding, Intra-Table `ORDER BY id ASC` Lock Order & Cross-Reporter Isolation)**: Authorized defenders may transition a report from `TRIAGING` to `DUPLICATE` by linking a valid canonical parent `duplicate_of_report_id` within the same `organization_id` (enforced via composite FK `(organization_id, duplicate_of_report_id)` and check constraint `duplicate_of_report_id <> id`), without exposing the parent report's ciphertext, attachments, or reporter identity to the duplicate submitter. To prevent intra-table deadlocks when two defenders concurrently mark two reports as duplicates of each other, the transaction locks `2. organizations FOR UPDATE` and then locks **both `report_id` and `duplicate_of_report_id` in deterministic ascending primary-key order (`SELECT id FROM bbt_core.reports WHERE organization_id = :org_id AND id IN (:report_id, :duplicate_of_report_id) ORDER BY id ASC FOR UPDATE`)** before verifying that the parent report is not itself a `DUPLICATE` and updating `report_id`.
  * **FR-5.5b (P2, Secondary — Candidate Duplicate Filter Helper)**: The triage desk provides an optional client-side filter helper suggesting open reports in the same `asset_scope` and `operational_label`.

### 3.6 Git-Linked & Configuration-Snapshot Remediation Verification (`FR-6` — MVP Feature 5)

* **FR-6.1 (P1, Core — Numbered Remediation Attempts, Three-Step Fix-to-Retest Workflow & Proposal Cancellation)**:
  * **FR-6.1a (Step 1 — Propose Fix: `ACCEPTED -> FIX_PROPOSED`)**: To transition a report from `ACCEPTED` to `FIX_PROPOSED`, an authorized defender in `REPORT_RECIPIENT` creates a numbered `REMEDIATION_RECORD` (`remediation_attempt_no = 1, 2, ...`, UUID `remediation_record_id`, `status = 'PROPOSED'`) specifying `evidence_type` (`CODE_COMMIT` or `CONFIG_INFRASTRUCTURE`) and an encrypted remediation summary (`remediation_notes_ciphertext`, Class B).
  * **FR-6.1b (Step 2 — Record Target Deployment)**: On a `FIX_PROPOSED` record, the defender records the target deployment environment (`Staging`, `Pre-Production`, or `Production`), `deployed_version` string, and `deployed_at` timestamp confirming where the candidate fix is live.
  * **FR-6.1c (Step 3 — Request Retest: `FIX_PROPOSED -> RETEST_PENDING`)**: Only after `deployed_at` and `deployment_env` are non-null on the active `remediation_record_id` may the defender transition the report from `FIX_PROPOSED` to `RETEST_PENDING` (starting the 14-day `retest_timeout_due` timer), which dispatches a metadata-only retest invitation bound to that specific `remediation_record_id` and `remediation_attempt_no`.
  * **FR-6.1d (Cancel Proposed Fix Before Retest: `FIX_PROPOSED -> ACCEPTED`)**: If a proposed fix in `FIX_PROPOSED` is discovered to be flawed or superseded before requesting a retest, an authorized defender in `REPORT_RECIPIENT` may transition **`FIX_PROPOSED -> ACCEPTED` (`CANCEL_PROPOSED_FIX`)** with Class C `audit_justification_ciphertext`, marking `remediation_record_id` as `SUPERSEDED` and requiring `remediation_attempt_no = N + 1` for the next fix proposal.
* **FR-6.2 (P1, Core — GitHub REST API v3 Commit Existence, `BASE...HEAD` Ancestry & Signature Metadata)**:
  * **FR-6.2a (Commit Existence & Signature Metadata)**: For `CODE_COMMIT` evidence (executed outside any long-lived database transaction), the server queries `GET /repos/{owner}/{repo}/commits/{commit_sha}` to verify that the 40-character hexadecimal SHA exists in the repository, recording the commit timestamp, author login/email metadata, and GitHub's `commit.verification.verified` boolean (`github_signature_verified`). Retrieving commit author metadata is explicitly distinguished from cryptographic identity verification.
  * **FR-6.2b (Explicit `BASE...HEAD` Branch Ancestry Check)**: The server queries `GET /repos/{owner}/{repo}/compare/{base}...{head}` with **`base = proposed_commit_sha`** and **`head = target_branch`**. Under GitHub's `BASE...HEAD` semantics, `proposed_commit_sha` is a merged ancestor of `target_branch` (or is the branch tip itself) if and only if the response `status` is **`ahead`** or **`identical`** (`behind_by == 0`). The server persists `verified_branch_head_sha` and `verified_at`, rejecting unmerged or divergent commits (`status == "behind"` or `"diverged"`) with HTTP `422 Unprocessable Entity`.
* **FR-6.3 (P1, Core — Encrypted Configuration Snapshot (`<= 160 KiB` Incompressible Plaintext / `<= 256 KiB` Armored Ciphertext) & SHA-256 Hash Binding)**: For `CONFIG_INFRASTRUCTURE` evidence, because a bare hash cannot reconstruct the configuration change for reviewer or researcher inspection, the defender selects or pastes a redacted configuration diff/manifest of **`<= 160 KiB` (`163,840 bytes`) raw UTF-8 plaintext input** in the browser. The browser computes its 64-character SHA-256 hash (`config_hash`) over the raw UTF-8 plaintext via WebCrypto and encrypts the configuration diff/manifest as a Class B OpenPGP v6 `SEIPDv2` payload (`config_artifact_ciphertext`, encrypted for `REPORT_RECIPIENT` [up to 10 defenders] + Submitter + `recovery_public_key` with OpenPGP compression explicitly disabled [`compression = openpgp.enums.compression.uncompressed`] to prevent compression-oracle side channels). Because **`160 KiB` (`163,840 bytes`) of incompressible raw data** expands under Base64 (`4/3` expansion = `218,456 bytes`) plus 12 Curve25519 PKESK packets, SEIPDv2 AEAD chunk headers/tags, ASCII-armor headers/checksums, and 64-column CRLF line breaks (`~6–8 KiB`) to **`~226 KiB` (`~231,424 bytes`)**, any valid `<= 160 KiB` plaintext input is mathematically guaranteed to fit within the hard **`<= 256 KiB` (`262,144 bytes`)** `config_artifact_ciphertext` ceiling (`~30 KiB` safety margin) enforced by both client and server (`TC-VCS-03`).
* **FR-6.4 (P1, Core — Private Repository GitHub Credential Lifecycle & Rate-Limit Aware Error Classification)**:
  * `ORG_OWNER` (with step-up TOTP MFA) may configure or rotate a fine-grained, read-only GitHub Personal Access Token (`Contents: Read-only`) in `/settings/integrations`, stored encrypted at rest using AES-256-GCM (`github_pat_ciphertext`) and revocable at any time.
  * **Strict Verification Rule & GitHub `403` vs. `429` Rate-Limit Disambiguation**: Because GitHub REST API v3 returns **either HTTP `429` or HTTP `403`** when primary or secondary rate limits are exceeded, the server inspects the response headers (`x-ratelimit-remaining == "0"` or `retry-after` header present) and JSON error message (`"rate limit"` or `"secondary rate limit"`) before classifying any `403` response. If GitHub API verification fails during a `CODE_COMMIT` proposal, **the report remains in `ACCEPTED`** and the server returns:
    1. **Rate Limit or Upstream Outage (`HTTP 429`, `HTTP 5xx`, or `HTTP 403` where `x-ratelimit-remaining == "0"`, `retry-after` is present, or message matches `"rate limit"`)** -> returns **`503 GITHUB_RATE_LIMIT_OR_OUTAGE`** (forwarding the computed `Retry-After` seconds so the defender can retry once the rate-limit window resets).
    2. **Authentication or Scope Error (`HTTP 401`, or `HTTP 403` where `x-ratelimit-remaining != "0"` and no rate-limit header/message is present)** -> returns **`422 GITHUB_AUTH_OR_PERMISSION_ERROR`** (instructing `ORG_OWNER` to refresh or grant `Contents: Read-only` on the PAT).
    3. **Commit Missing or Not Merged (`HTTP 404` or compare `status IN ('behind', 'diverged')`)** -> returns **`422 COMMIT_NOT_FOUND_OR_NOT_ANCESTOR`**.

### 3.7 15-State Lifecycle FSM, Attested Retest & Redacted Closure Exports (`FR-7` — MVP Feature 5)

* **FR-7.1 (P1, Core — Deterministic 15-State Vulnerability Lifecycle FSM & Atomic Concurrency)**:
  * **FR-7.1a (Exact 15 States)**: Every `REPORT` exists in exactly one of **15 distinct lifecycle states**:
    - **6 Active Workflow States**: `(1) NEW`, `(2) TRIAGING`, `(3) NEED_MORE_INFO`, `(4) ACCEPTED`, `(5) FIX_PROPOSED`, `(6) RETEST_PENDING`.
    - **3 Remediation Closure States**: `(7) VERIFIED_RESEARCHER`, `(8) VERIFIED_INTERNAL`, `(9) CLOSED_UNVERIFIED_TIMEOUT`.
    - **6 Non-Remediation Terminal States**: `(10) CLOSED_INCOMPLETE`, `(11) RISK_ACCEPTED`, `(12) REJECTED_INVALID`, `(13) DUPLICATE`, `(14) REJECTED_SPAM`, `(15) WITHDRAWN`.
  * **FR-7.1b (Atomic Optimistic Concurrency, Universal 6-Step Canonical Lock Order & Intra-Table `ORDER BY id ASC` Rule)**:
    1. *Universal 6-Table Lock Hierarchy*: Because every mutating write updates `organizations` via the quota byte-accounting trigger (`Section 2.6`) and appends to `organization_audit_heads` (`FR-8.5b`), **every mutating transaction across the entire system acquires row locks strictly in ascending order across the 6-table hierarchy**:
       `1. cluster_storage_state [when R2 or emergency DB buffer changes] -> 2. organizations -> 3. programs [when program-scoped] -> 4. submission_sessions [when consuming a session] -> 5. reports [when report-scoped] -> 6. organization_audit_heads`.
       For any endpoint keyed by `report_id` (including guest mutations in `FR-1.6f`, retest attestations in `UC-04`, and key re-wrapping in `FR-3.8b`), the transaction first resolves `organization_id` via a non-locking `SELECT` and then locks **`2. organizations FOR UPDATE` BEFORE `5. reports FOR UPDATE`** so the subsequent trigger `UPDATE` on `organizations` already holds the `organizations` lock and never inverts `reports -> organizations`.
    2. *Deterministic Intra-Table Multi-Row Ordering (`ORDER BY id ASC FOR UPDATE`)*: Whenever a transaction locks multiple rows in the same table (such as parent+child duplicate linking in `FR-5.5a` or multi-row key revocation in `FR-3.8a`), rows within that table are locked strictly in **`ORDER BY id ASC FOR UPDATE`** order, accompanied by bounded application retry handling (`<= 2` retries with `20–50 ms` random jitter if PostgreSQL ever raises `SQLSTATE '40P01'`).
    3. *Optimistic `state_version` Guard*: Report transitions assert `WHERE id = :report_id AND organization_id = :org_id AND state = :expected_state AND state_version = :expected_version`, incrementing `state_version = state_version + 1`, updating `reports.last_audit_seq_no` and `reports.last_report_chain_hash`, and inserting the linked evidence and `audit_events` row in the same commit. Simultaneous conflicting actions (e.g., a researcher submitting `RETEST_FAILED` at the exact instant a defender submits `CLOSED_UNVERIFIED_TIMEOUT`) result in the second transaction affecting `0` rows and returning HTTP `409 Conflict`.
* **FR-7.2 (P1, Core — Three Distinct Remediation Closure States Bound to `remediation_record_id`, Sub-Reserve & PL/pgSQL Subtransaction Atomic Pause Under Lock)**: From `RETEST_PENDING`, a report transitions to remediation closure exclusively via one of three terminal states, each mandatory-linked via foreign key to the active `remediation_record_id` (`remediation_attempt_no`):
  1. `VERIFIED_RESEARCHER`: The submitting researcher (`HUNTER` or `GUEST` with OpenPGP detached signature `X-Guest-Signature` binding `remediation_record_id` per `FR-1.6f`) confirms the fix on the target environment and submits `verification_notes_ciphertext` (Class B, permitted to draw from the dedicated `1.0 MiB` active-report researcher response sub-reserve and the `300 KiB` Priority-0 reserve allowlist in `Section 2.6`).
  2. `VERIFIED_INTERNAL`: An authorized `PROGRAM_DEFENDER` in `REPORT_RECIPIENT` certifies the fix internally with `verification_notes_ciphertext` (Class B, counted against the `6 MiB` reserve) and a boolean `verifier_authored_fix` conflict-of-interest disclosure.
  3. `CLOSED_UNVERIFIED_TIMEOUT`: Closed by an authorized defender in `REPORT_RECIPIENT` after `retest_timeout_due <= now() AND capacity_deadline_paused = false` (`>= 14 days` of genuine researcher inactivity in `RETEST_PENDING`), requiring `audit_justification_ciphertext` (Class C). If the researcher posts a `RESEARCHER_ORG` message reporting a target environment outage/blocker during `RETEST_PENDING`, `retest_timeout_due` is extended by 7 days; defender-only comments never advance or satisfy the timer. Furthermore, when a researcher submits a retest outcome (`VERIFIED_RESEARCHER` or `RETEST_FAILED`) or blocker reply, **the Node.js API client opens the outer transaction (`BEGIN`) and invokes `bbt_core.fn_process_researcher_response_or_pause` holding `2. organizations FOR UPDATE -> 5. reports FOR UPDATE` (`Section 2.6`)**: (a) if the report already reached a terminal state before the lock was acquired, the function returns `{"outcome": "CONFLICT_409", "http_status": 409, "error_code": "REPORT_STATE_CONFLICT_OR_ALREADY_CLOSED", "deadline_paused": false}` without setting a pause; (b) if the report is still in `RETEST_PENDING`, the payload write runs inside a nested PL/pgSQL `BEGIN ... EXCEPTION WHEN SQLSTATE 'P0001' THEN ... END` subtransaction block: if `trg_enforce_tenant_db_quota` raises one of the four recognized logical quota codes (`413` or `507`, re-raising any other `P0001` via `RAISE;`), PostgreSQL automatically rolls back the inner block's partial writes while **retaining the outer `FOR UPDATE` locks**, the `EXCEPTION` handler sets `app.quota_exempt_reason = 'CAPACITY_DEADLINE_PAUSE'`, updates `capacity_deadline_paused = true, capacity_paused_at = COALESCE(capacity_paused_at, now())`, and returns `{"outcome": "PAUSED_QUOTA", "deadline_paused": true}`, and **the API client `COMMIT`s the outer transaction before returning `413` / `507` (`"deadline_paused": true`)**, blocking `CLOSED_UNVERIFIED_TIMEOUT` until capacity is restored below `95%` and `retest_timeout_due` resumes at **`GREATEST(retest_timeout_due + (now() - capacity_paused_at), now() + interval '7 days')`**; or (c) if physical database storage is exhausted (`SQLSTATE '53100' disk_full`), the API client issues `ROLLBACK` on the outer transaction and returns **`HTTP 503 Service Unavailable` (`DATABASE_PHYSICAL_STORAGE_EXHAUSTED`, `"deadline_paused": false`)**. Never counted as a verified fix in metrics or exports.
* **FR-7.3 (P1, Core — Non-Remediation Terminal States & Authority Rules)**:
  * `WITHDRAWN`: Voluntarily retracted by the submitting researcher (`HUNTER` or `GUEST` with `X-Guest-Signature`) from **either `NEW` or `TRIAGING`**. Permanently terminal (`non-reopenable`).
  * `RISK_ACCEPTED`: Formal operational risk acceptance from **either `TRIAGING` or `ACCEPTED`**, restricted **exclusively to `ORG_OWNER` with step-up TOTP MFA (`FR-1.3c`)**, requiring `risk_rationale_ciphertext` (Class C) and a scheduled `risk_review_date`. Never counted as a remediated vulnerability.
  * `CLOSED_INCOMPLETE`: Automatic transition from `NEED_MORE_INFO` after `info_timeout_due <= now() AND capacity_deadline_paused = false` (`>= 14 days` without a researcher reply).
  * `REJECTED_INVALID`: Transitioned from `TRIAGING` by an authorized defender in `REPORT_RECIPIENT` with a Class A `rejection_code` enum and Class B `rejection_reason_ciphertext`.
  * `DUPLICATE`: Transitioned from `TRIAGING` by an authorized defender in `REPORT_RECIPIENT` linked to an existing `duplicate_of_report_id` in the same organization (`FR-5.5a`).
  * `REJECTED_SPAM`: Transitioned from `NEW` or `TRIAGING` by an authorized defender in `REPORT_RECIPIENT` for automated scanner noise.
* **FR-7.4 (P1, Core — `RETEST_FAILED` Loopback Bound to Remediation Attempt)**: If empirical retesting shows the vulnerability persists or the patch is bypassed, submitting a `RETEST_FAILED` attestation (bound to the tested `remediation_record_id` with `verification_notes_ciphertext`, permitted to use the `1.0 MiB` active-report researcher response sub-reserve and the `300 KiB` Priority-0 reserve allowlist) atomically marks `remediation_record_id.status = 'FAILED'` and transitions the report from `RETEST_PENDING` back to `ACCEPTED`. A subsequent fix proposal must create a new `REMEDIATION_RECORD` (`remediation_attempt_no + 1`), preventing any prior retest record from associating with the new fix.
* **FR-7.5 (P1, Core — Automated 14-Day Clarification Timeout, Priority-0 Sub-Reserve & PL/pgSQL Subtransaction Atomic Pause Under Lock)**: When a defender transitions `TRIAGING -> NEED_MORE_INFO`, the server sets `info_timeout_due = now() + interval '14 days'`. This timer is reset/cleared **only when the submitting researcher (`HUNTER` or `GUEST`) posts a `RESEARCHER_ORG` clarification response** (which is guaranteed access to both the dedicated `1.0 MiB` active-report response sub-reserve and the `300 KiB` Priority-0 security reserve allowlist in `Section 2.6`), atomically transitioning `NEED_MORE_INFO -> TRIAGING` (`info_timeout_due = NULL, capacity_deadline_paused = false, capacity_paused_at = NULL`). Defender comments or internal notes in `NEED_MORE_INFO` do **not** reset `info_timeout_due`. Inside the client-owned outer transaction (`BEGIN ... COMMIT`), **`bbt_core.fn_process_researcher_response_or_pause` locks `2. organizations FOR UPDATE -> 5. reports FOR UPDATE`**: (a) if the report was already closed (`CLOSED_INCOMPLETE`) before the researcher request obtained the lock, the function returns `HTTP 409 Conflict` (`REPORT_STATE_CONFLICT_OR_ALREADY_CLOSED`) without mutating the closed report; (b) if the report is still in `NEED_MORE_INFO` and a recognized logical quota code (`413` or `507`) rejects the payload inside the nested PL/pgSQL `BEGIN ... EXCEPTION WHEN SQLSTATE 'P0001'` block (re-raising any non-quota `P0001` via `RAISE;`), the inner block's partial writes roll back automatically while **retaining the outer `FOR UPDATE` locks**, the `EXCEPTION` handler sets `app.quota_exempt_reason = 'CAPACITY_DEADLINE_PAUSE'`, updates `capacity_deadline_paused = true, capacity_paused_at = COALESCE(capacity_paused_at, now())`, and **the API client `COMMIT`s the outer transaction before returning `413` / `507` (`"deadline_paused": true`)**, blocking `CLOSED_INCOMPLETE` until storage is restored below `95%` and `info_timeout_due` resumes at **`GREATEST(info_timeout_due + (now() - capacity_paused_at), now() + interval '7 days')`** (`Section 2.6`); or (c) if physical database storage is exhausted (`SQLSTATE '53100' disk_full`), the API client rolls back the outer transaction and returns **`HTTP 503 Service Unavailable` (`DATABASE_PHYSICAL_STORAGE_EXHAUSTED`, `"deadline_paused": false`)**. Otherwise, when `info_timeout_due <= now() AND capacity_deadline_paused = false`, the hourly cron job (`FR-5.4`) transitions the report to `CLOSED_INCOMPLETE`.
* **FR-7.6 (P1, Core — Explicit Regression & False-Positive Reopening Rules)**:
  * Reports in `VERIFIED_RESEARCHER`, `VERIFIED_INTERNAL`, `CLOSED_UNVERIFIED_TIMEOUT`, `CLOSED_INCOMPLETE`, `RISK_ACCEPTED`, `REJECTED_INVALID`, or `DUPLICATE` may be reopened to `TRIAGING` (via event `REOPEN_REGRESSION`) by an authorized defender in `REPORT_RECIPIENT` or `ORG_OWNER` with mandatory `audit_justification_ciphertext` (Class C).
  * To recover accidental spam classifications, a report in `REJECTED_SPAM` may be reopened to `TRIAGING` **exclusively by `ORG_OWNER` with step-up TOTP MFA** and mandatory `audit_justification_ciphertext` (Class C).
  * Only `WITHDRAWN` (researcher-retracted) is permanently non-reopenable.
* **FR-7.7 (P2, Secondary — Export-Allowlisted Redacted Closure Evidence Export, `closure_report_seq_no` Binding & Standalone Verifier Contract `bbt-closure-export-v1`)**:
  * **FR-7.7a (Top-Level JSON Envelope, `closure_report_seq_no = M` Binding & Embedded PDF Associated File)**: Authorized defenders in `REPORT_RECIPIENT` or `ORG_OWNER` may generate a **Redacted Closure Evidence Export (`bbt-closure-export-v1`)** as `.bbt-closure-export.json` or `.bbt-closure-export.pdf` (where the PDF embeds the exact `.bbt-closure-export.json` byte stream as an **ISO 32000-2 Associated File [`EmbeddedFiles`]** so the standalone verifier validates either the JSON file directly or the embedded JSON stream extracted from the PDF). Because a closed report can subsequently accumulate non-transition audit events (`M < j <= K`, such as `MASTER_RECOVERY_FETCH_INITIATED`, `HISTORICAL_ACCESS_GRANTED`, or `RESEARCHER_KEY_REWRAPPED`) or have undergone prior reopen cycles (`REOPEN_REGRESSION`) before its final closure, `export_payload.summary` explicitly includes **`closure_report_seq_no = M` (`1 <= M <= K`)** identifying the exact event `report_chain[M]` that transitioned the report into its current `summary.terminal_state`. The top-level JSON structure is:
    `{ "schema": "bbt-closure-export-v1", "export_payload": { "summary": {...}, "report_chain": [...], "unredacted_salts": {...}, "terminal_checkpoint_receipt": {...} }, "export_signature": { "checkpoint_key_id": "<id>", "algorithm": "Ed25519", "signature_hex": "<128-hex>" } }`:
    1. *`export_payload.summary` (Table 2.1 External Export Allowlist)*: `report_id`, `organization_slug`, `program_slug`, `operational_label`, `cvss_vector`, `cvss_score`, `remediation_attempt_no`, `evidence_type`, `config_hash`, `deployment_env`, `deployed_version`, `deployed_at`, `terminal_state`, **`closure_report_seq_no` (`M`, `1 <= M <= K`)**, `submitted_at`, `closed_at`, and optional redactable fields `asset_scope` and `commit_sha`/`branch_name` (**never** raw `organization_id` or `actor_id` UUIDs).
    2. *`export_payload.report_chain` (`report_seq_no = 1..K`)*: Every event in the report's `report_chain_hash` sequence (`1..K`) is exported with **all 20 exact inputs required to recompute `report_chain_hash` (`FR-8.5c`)**: `{ report_id, report_seq_no, state_version, operational_label, cvss_vector, cvss_score, actor_role_category, actor_commitment, action, from_state, to_state, remediation_record_id, remediation_attempt_no, deployment_env, deployed_version, asset_scope_commitment, evidence_commitment, justification_seipdv2_sha256, timestamp_iso8601, prev_report_chain_hash, report_chain_hash }`.
    3. *`export_payload.terminal_checkpoint_receipt` & `export_signature` (Non-Self-Referential Signing Input)*: `terminal_checkpoint_receipt` contains the final event's (`report_seq_no = K`) Ed25519 **Audit Checkpoint Receipt** (`FR-8.5d`), which binds `organization_slug` and `org_commitment = Commit("organization_id", org_salt_hex, organization_id)` (never raw `org_id`) alongside `report_chain_hash[K]` and `tenant_row_hash[K]`. The top-level **`export_signature.signature_hex`** is an Ed25519 signature produced by `AUDIT_CHECKPOINT_PRIVATE_KEY` (`checkpoint_key_id`) strictly over **`RFC8785_JCS(export_payload)`** (excluding the outer `export_signature` object itself).
  * **FR-7.7b (Explicit Verification Boundary for `closure_report_seq_no = M`, Post-Closure Events `M < j <= K`, Unredacted vs. Redacted Fields & Tamper Outcomes)**:
    - *Mandatory Summary-to-Closure-Event (`M`) Equality & Post-Closure State Invariant (`M < j <= K`)*: A **standalone offline verifier (with zero database access)** first verifies `export_signature.signature_hex` over `RFC8785_JCS(export_payload)` and `terminal_checkpoint_receipt` (anchored at `report_seq_no = K`), then recomputes `report_chain_hash[1..K]` from genesis (`"0000...0000"`), verifies `1 <= summary.closure_report_seq_no (M) <= K`, and **asserts exact equality between `export_payload.summary` and the active closure event `report_chain[M]`**:
      1. `summary.submitted_at == report_chain[1].timestamp_iso8601`
      2. `summary.closed_at == report_chain[M].timestamp_iso8601` and `summary.terminal_state == report_chain[M].to_state` (where `report_chain[M].from_state != report_chain[M].to_state`)
      3. `summary.cvss_vector == report_chain[M].cvss_vector`, `summary.cvss_score == report_chain[M].cvss_score`, `summary.remediation_attempt_no == report_chain[M].remediation_attempt_no`, `summary.deployment_env == report_chain[M].deployment_env`, and `summary.deployed_version == report_chain[M].deployed_version`
      4. **Post-Closure Non-Transition Invariant (`M < j <= K`)**: For every subsequent audit event `j` after `M` (`M < j <= K`, such as `MASTER_RECOVERY_FETCH_INITIATED`, `HISTORICAL_ACCESS_GRANTED`, or `RESEARCHER_KEY_REWRAPPED`), the verifier asserts **`report_chain[j].from_state == summary.terminal_state AND report_chain[j].to_state == summary.terminal_state`**, proving that the report remained continuously in `summary.terminal_state` through the terminal receipt `K` while preserving any earlier reopen history (`1 <= i < M`).
    - *Unredacted Mode & Exact Tamper Distinction (`TC-EXPORT-01a`)*: For any redactable field left unredacted (`asset_scope` or `commit_sha`/`branch_name`/`config_hash` at `report_chain[M]`), `export_payload.unredacted_salts` includes the 128-bit hex salt (`asset_salt_hex`, `evidence_salt_hex`) from `audit_events.commitment_salts_json`, and the verifier recomputes `asset_scope_commitment` and `evidence_commitment` via `Commit(field, salt_hex, value)` (`FR-8.5c`). Consequently: (1) modifying any field inside `report_chain[1..K]` or any unredacted commitment value/salt (`asset_scope`, `commit_sha`, `branch_name`, `config_hash`) causes **both `report_chain_hash` (or `Commit(...)`) recomputation and `export_signature` verification to fail**; and (2) modifying a field inside `export_payload.summary` (or altering a post-closure event's state) causes **`export_signature` verification and the Summary-to-Closure-Event (`M`) check to fail**.
    - *Redacted Mode (`asset_scope` or `commit_sha` set to `"[REDACTED]"`) & Narrowed Claim (`TC-EXPORT-01b`)*: When the exporter toggles redaction on `asset_scope` or `commit_sha`/`branch_name`, the export omits the corresponding plaintext string and salt from `unredacted_salts`, retaining only the 64-hex `asset_scope_commitment` or `evidence_commitment` inside `report_chain`. In this mode, the standalone verifier validates `export_signature`, `terminal_checkpoint_receipt`, Summary-to-Closure-Event (`M`) equality on all non-redacted fields, post-closure state invariance (`M < j <= K`), and the entire `report_chain_hash[1..K]` sequence, **and explicitly labels the redacted field as `COMMITMENT_VERIFIED_VALUE_REDACTED` (proving chain continuity and that the export was authorized, without proving the hidden string value of the redacted field)**.

### 3.8 Application Hardening, Forced RLS, Upload Reservations & Hash-Chained Audit Ledger (`FR-8` — MVP Features 4 & 5)

* **FR-8.1 (P1, Core — Markdown AST Sanitization & OWASP XSS Corpus Neutralization)**: All decrypted Class B and Class C Markdown fields shall be parsed into an Abstract Syntax Tree (AST) and sanitized via `unified` / `remark-parse` / `rehype-sanitize` using a strict allowlist (forbidding `<script>`, `<iframe>`, `<object>`, `<svg>`, inline `style`, `javascript:`, `data:`, and `on*` event attributes), neutralizing **100% of the defined 100-vector OWASP Cross-Site Scripting (XSS) Filter Evasion test corpus**.

    1. *`search_path`, Privilege Restriction & Unconditional First-Line GUC Reset*: Every `SECURITY DEFINER` function is owned by `bbt_fn_owner`, schema-qualifies all table and operator references (`bbt_core.<table>`), declares **`SET search_path = pg_catalog, bbt_core, pg_temp`** (placing **`pg_temp` explicitly last** per PostgreSQL 16 documentation so session temporary tables/functions can never shadow application or catalog objects), and enforces `REVOKE ALL ON FUNCTION ... COMMIT` or `ROLLBACK`) whenever a validated researcher (`HUNTER` or `GUEST`) submits a clarification reply (`NEED_MORE_INFO`) or retest submission/blocker reply (`RETEST_PENDING`). * **FR-8.5 (P1, Core — Audit-Head Locking, Universal `event_digest`, Export-Safe `org_commitment` / `report_chain_hash` & External Checkpoint Trust Model)**:
  * **FR-8.5a (Privilege Separation Between `organization_audit_heads` and `audit_events`)**: The `bbt_app_runtime` and `bbt_fn_owner` roles are granted **`SELECT, INSERT` ONLY on `bbt_core.audit_events`** (`0` `UPDATE`, `DELETE`, or `TRUNCATE` privileges) and **`SELECT, INSERT, UPDATE` on `bbt_core.organization_audit_heads`** (`organization_id UUID PRIMARY KEY, last_seq_no BIGINT NOT NULL DEFAULT 0, last_row_hash CHAR(64) NOT NULL`). `audit_events` enforces `UNIQUE (organization_id, tenant_seq_no)` and `UNIQUE (organization_id, report_id, report_seq_no)`.
  * **FR-8.5b (6-Step Canonical Lock Order, `organization_audit_heads` Serialization & Report Audit Head Update)**: Every tenant's `organization_audit_heads` row is created with `last_seq_no = 0` and `last_row_hash = "0000...0000"` during onboarding (`UC-06`). When recording any auditable action, the transaction follows the universal 6-table canonical lock order (`1. cluster_storage_state [when R2 or emergency DB buffer changes] -> 2. organizations -> 3. programs -> 4. submission_sessions [when consuming a session] -> 5. reports [when report-scoped] -> 6. organization_audit_heads`, with `ORDER BY id ASC FOR UPDATE` for any multi-row table access per `FR-7.1b`), executes `SELECT last_seq_no, last_row_hash FROM bbt_core.organization_audit_heads WHERE organization_id = :org_id FOR UPDATE`, allocates `tenant_seq_no = last_seq_no + 1`, and:
    - If **report-scoped (`report_id IS NOT NULL`)**: allocates `report_seq_no = report.last_audit_seq_no + 1`, computes `report_chain_hash` from `prev_report_chain_hash = report.last_report_chain_hash`, **explicitly executes `UPDATE bbt_core.reports SET last_audit_seq_no = :report_seq_no, last_report_chain_hash = :report_chain_hash WHERE id = :report_id AND organization_id = :org_id`**, inserts the `audit_events` row (including `commitment_salts_json`), and updates `organization_audit_heads` in the **same atomic transaction**.
    - If **organization-scoped (`report_id IS NULL`)** (e.g., membership additions/removals, `PROGRAM_DEFENDER` updates, GitHub PAT changes, Master Recovery Key rotation): sets `report_seq_no = NULL` and `report_chain_hash = NULL`, inserts the `audit_events` row with its full `event_digest`, and updates `organization_audit_heads` in the **same atomic transaction**.
  * **FR-8.5c (Salted Commitment Formula, `org_commitment`, Universal `event_digest`, Export-Compatible `report_chain_hash` & Tenant Chain `tenant_row_hash`)**:
    1. *Domain-Separated Salted Commitment Formula & Salt Persistence*: Each event generates four 128-bit CSPRNG salts (`org_salt_hex`, `actor_salt_hex`, `asset_salt_hex`, `evidence_salt_hex`) stored in internal column `audit_events.commitment_salts_json` (never exposed to researchers, and emitted in `FR-7.7` `unredacted_salts` only for unredacted fields) and computes:
       `Commit(field, salt_hex, val) = SHA-256(RFC8785_JCS({ domain: "bbt-commit-v1", field: field, salt_hex: salt_hex, value: val }))`
       producing **`org_commitment = Commit("organization_id", org_salt_hex, organization_id)`**, `actor_commitment = Commit("actor_id", actor_salt_hex, actor_id)`, `asset_scope_commitment = Commit("asset_scope", asset_salt_hex, asset_scope)`, and `evidence_commitment = Commit("evidence", evidence_salt_hex, { evidence_type, commit_sha, branch_name, config_hash })`.
    2. *Universal Canonical Event Digest (`event_digest` — Computed for Every Org-Scoped and Report-Scoped Event)*:
       `event_digest = SHA-256(RFC8785_JCS({ org_id, org_commitment, tenant_seq_no, scope_type: "ORG"|"REPORT", report_id, report_seq_no, state_version, actor_type, actor_id, actor_role_category, actor_commitment, action, target_entity_type, target_entity_id, from_state, to_state, remediation_record_id, evidence_payload_sha256, justification_seipdv2_sha256, timestamp_iso8601 }))`.
       Because `event_digest` binds `actor_id`, `action`, `target_entity_type`, `target_entity_id`, `evidence_payload_sha256`, and `timestamp_iso8601` for **every** event, modifying a membership-removal or integration-change event's actor, action, or target immediately invalidates `event_digest` and `tenant_row_hash` (`TC-SEC-05c`).
    3. *Export-Compatible Per-Report Chain (`report_chain_hash` — Computed for Report-Scoped Events `report_seq_no = 1..K`)*:
       `report_chain_hash = SHA-256(RFC8785_JCS({ report_id, report_seq_no, state_version, operational_label, cvss_vector, cvss_score, actor_role_category, actor_commitment, action, from_state, to_state, remediation_record_id, remediation_attempt_no, deployment_env, deployed_version, asset_scope_commitment, evidence_commitment, justification_seipdv2_sha256, timestamp_iso8601, prev_report_chain_hash }))`.
       All 20 fields in this JSON object are included in `bbt-closure-export-v1` (`FR-7.7`), allowing an external verifier to recompute `report_chain_hash[1..K]` without database access or internal UUID leakage.
    4. *Export-Safe Per-Tenant Chain (`tenant_row_hash` — Uses `organization_slug` + `org_commitment` Instead of Raw `org_id`)*:
       `tenant_row_hash = SHA-256(RFC8785_JCS({ organization_slug, org_commitment, tenant_seq_no, event_digest, report_id, report_seq_no, report_chain_hash, prev_tenant_row_hash }))`.
  * **FR-8.5d (External Checkpoint Signing Key, Privacy-Safe Receipt & Trust Model)**:
    1. *Checkpoint Key Ownership & Distribution*: The application server holds a dedicated Ed25519 **Platform Audit Checkpoint Signing Key** (`AUDIT_CHECKPOINT_PRIVATE_KEY`, identified by `checkpoint_key_id`). The corresponding public key and rotation history (`checkpoint_key_id`, `public_key_hex`, `valid_from`, `valid_until`) are published at `GET /api/v1/audit/checkpoint-keys` and embedded as a comment header inside each organization's cleartext-signed `/.well-known/security.txt` manifest.
    2. *Privacy-Safe Signed Receipt & Outbox Guarantee (Zero Raw `org_id` Leakage)*: Every `audit_events` insertion generates an Ed25519-signed **Audit Checkpoint Receipt** over `RFC8785_JCS({ checkpoint_key_id, organization_slug, org_commitment, tenant_seq_no, event_digest, tenant_row_hash, report_id, report_seq_no, report_chain_hash, timestamp_iso8601 })` stored on the event, included in `bbt-closure-export-v1` as `terminal_checkpoint_receipt` (`FR-7.7a`), and enqueued in `notification_outbox` in the same transaction—binding the tenant via `organization_slug` and `org_commitment` without exposing the internal `organization_id` UUID in exported files or notifications.
    3. *Explicit Tamper-Resistance Boundary*: Independently retained checkpoint receipts detect any retroactive database-only tampering. A simultaneous compromise of both PostgreSQL and `AUDIT_CHECKPOINT_PRIVATE_KEY` could sign forged receipts for rewritten history, which remains detectable when compared against previously delivered external receipts. An audit record proves **who attested to an action, when, and against which commit/config hash**—not the objective absence of residual software bugs.

### 4.1 Formal Textual Use Case Specifications (`UC-01` to `UC-07`)

#### Use Case UC-01: Submit Encrypted Vulnerability Report (Registered Hunter & Guest Branches)

* **Primary Actor**: Ethical Security Researcher (`Hunter` [Registered] or `Guest Hunter` [Account-Less]).
* **Preconditions**: Researcher is viewing an organization's active public program page (`/programs/[slug]`, P1 `FR-1.5a`; or holds a valid private program invitation token `token_hash`, P2 `FR-1.5b`). If registered, the researcher does not hold an active `USER_MEMBERSHIP` in the target organization.
* **Main Success Scenario**:
  1. Researcher selects an in-scope target asset (`asset_scope`), selects a coarse Class A `operational_label` enum, enters the specific vulnerability title, reproduction steps, optional suggested CVSS v3.1 vector (`cvss_suggested`), and optional PoC attachment (`<= 3` files, each `<= 25 MiB` [`26,214,400 bytes`] encrypted size, total report `<= 50 MiB` [`52,428,800 bytes`]).
  2. Browser completes Cloudflare Turnstile CAPTCHA once and calls `POST /api/v1/submission-sessions` (outside any DB lock) to create an `OPEN` 30-minute `submission_session_token` (`FR-3.5a`) and fetches the program's active `PROGRAM_DEFENDER` key versions (`recipient_set_version`) plus `recovery_public_key`.
  3. **Branch A (Registered `HUNTER`)**: Browser unlocks the researcher's existing RFC 9580 v6 Curve25519 `USER_KEY` (`submitter_key_id`) from `IndexedDB` (`s2kType = openpgp.enums.s2k.argon2`).
     **Branch B (Account-Less `GUEST`)**: Researcher enters (or copies) a Guest Recovery Passphrase; browser configures `OpenPGP.js v6` (`v6Keys = true`, `s2kType = openpgp.enums.s2k.argon2`, `aeadProtect = true`) and generates an ephemeral RFC 9580 v6 Curve25519 keypair in memory (`< 50 ms` target).
  4. **Optional Extension (When PoC Attachment Included)**: Browser generates a random 256-bit OpenPGP session key `K_file`, encrypts the attachment as a standard OpenPGP v6 SEIPDv2 binary message, computes `ciphertext_sha256`, and calls `POST /api/uploads/presign` with `submission_session_token`, `exact_ciphertext_bytes`, and `ciphertext_sha256`. Following the canonical lock order (`1. cluster_storage_state -> 2. organizations`), the server locks `cluster_storage_state` and the tenant's `organizations` row (`<= 19.0 MiB` new-report DB intake check, `<= 1.0 GiB` tenant / `<= 9.5 GiB` cluster R2 check), creates a 15-minute `upload_reservations` row (`status = 'RESERVED'`), and returns a presigned R2 `PUT` URL (`If-None-Match: *`). Browser uploads the ciphertext directly to Cloudflare R2.
  5. Browser encrypts all Class B fields (`title_ciphertext`, description, reproduction steps, impact, and `encrypted_file_key_packet` wrapping `K_file` if attachments are present) into multi-recipient OpenPGP v6 packets for the **Authoritative Class B Recipient Set** (`FR-3.3a`, `FR-3.5b`: active `PROGRAM_DEFENDER` keys `key_id` + `recovery_public_key` + submitter's public key).
  6. Browser dispatches `POST /api/v1/reports` with `submission_session_token`, `recipient_set_version`, Class A metadata, Class B ciphertexts, and any `reservation_id`s.
  7. Server first verifies any uploaded R2 objects via `HeadObjectCommand` (outside the DB transaction) and, for Branch B (`GUEST`), generates the 256-bit `access_token`, computes `guest_token_hash`, and encrypts `{ report_id, guest_actor_id, access_token }` to `REPORT.guest_public_key` (`encrypted_guest_credentials_armored`, `FR-1.6b`). Then, inside a single short PostgreSQL transaction following the canonical lock order (`2. organizations -> 3. programs -> 4. submission_sessions -> 5. reports -> 6. organization_audit_heads`), the server locks `submission_sessions FOR UPDATE` (checking `status == 'OPEN'` or returning the cached idempotent `cached_response_json` if `status == 'CONSUMED'` with matching `request_payload_sha256`), checks the **`95%` (`19.0 MiB` / `19,922,944 bytes`) new-report intake ceiling** (`Section 2.6`), validates `recipient_set_version`, marks `submission_sessions.status = 'CONSUMED'` (storing only `{ report_id, guest_actor_id, encrypted_guest_credentials_armored }` in `cached_response_json`—never a plaintext token), atomically binds any `upload_reservations` (`status = 'RESERVED' -> 'BOUND'`), snapshots active `PROGRAM_DEFENDER` keys into `REPORT_RECIPIENT` (`report_recipient_version = 1`), inserts the `REPORT` in state `NEW` (`state_version = 1`, `last_audit_seq_no = 1`), locks `organization_audit_heads` to append `tenant_seq_no` / `report_seq_no = 1` (`org_commitment`, `event_digest`, `report_chain_hash`, `tenant_row_hash`) to `audit_events`, and enqueues a metadata-only notification in `notification_outbox`.
  8. **Post-Submission Output**:
     - For **Branch A (`HUNTER`)**: Browser redirects to `/dashboard/submissions/BBT-RPT-XXXX`.
     - For **Branch B (`GUEST`)**: Server returns `report_id`, durable `guest_actor_id`, and `encrypted_guest_credentials_armored`. Browser decrypts `encrypted_guest_credentials_armored` in local memory using `ephemeral_private_key` to obtain `access_token`, encrypts `{ report_id, guest_actor_id, access_token, armored_private_key }` into a standard OpenPGP v6 password-encrypted `.bbt-recovery.json` Guest Recovery Package (`FR-1.6c`), stores the private key in `IndexedDB`, displays `/report/track/BBT-RPT-XXXX#token=<secret>`, and immediately scrubs the URI fragment via `window.history.replaceState`.
* **Extensions**:
  * *2a / 4a / 7a. Rate limit (`> 5 sessions/hr/IP`) or storage quota (`> 19.0 MiB` [`95%`] new-report DB intake, `> 1.0 GiB` tenant R2, or `> 9.5 GiB` cluster R2) exceeded*: Server rejects with HTTP `429 Too Many Requests` or `413 Payload Too Large` (`NEW_REPORT_INTAKE_QUOTA_EXCEEDED`, preserving the `1.0 MiB` active-report response sub-reserve).
  * *6a. Stale `recipient_set_version`*: Server returns HTTP `409 Conflict` with updated keyring (leaving `submission_sessions.status = 'OPEN'`); browser re-encrypts the text payload and re-wraps `K_file` (without re-uploading the R2 binary blob) and retries automatically.
  * *7b. Network drop & retry with same `submission_session_token`*: Because `submission_sessions` stores `request_payload_sha256` and `cached_response_json` (containing `encrypted_guest_credentials_armored` encrypted to `REPORT.guest_public_key`) on consumption, retrying an identical `POST /api/v1/reports` within 30 minutes returns the original `201 Created` response without creating a second report or exposing a plaintext token in the database.

#### Use Case UC-02: Decrypt, Claim for Triage & Score Vulnerability Report

* **Primary Actor**: Organization Triage Lead (`ORG_DEFENDER` with active `REPORT_RECIPIENT` key).
* **Preconditions**: Authenticated with `ORG_DEFENDER` role and active in `REPORT_RECIPIENT` for the report; report is in state `NEW` or `TRIAGING`.
* **Main Success Scenario**:
  1. Defender opens `/dashboard/reports/[id]`. Browser fetches the ciphertext record (`state_version`, `report_recipient_version`) and retrieves the defender's Argon2id-protected private key from `IndexedDB`.
  2. Defender enters their local encryption passphrase to unlock the private key (`s2kType = openpgp.enums.s2k.argon2`, `~200–400 ms` intentional, estimated cryptographic delay).
  3. Browser decrypts `title_ciphertext` and `encrypted_payload` in memory, sanitizes the Markdown AST via `rehype-sanitize`, and renders sanitized HTML.
  4. **Step 4a (Claim Intake: `NEW -> TRIAGING`)**: If the report is in `NEW`, the defender clicks "Begin Triage," atomically transitioning `NEW -> TRIAGING` (`state_version + 1`, locking `2. organizations -> 5. reports -> 6. organization_audit_heads`) and recording the assigned triager in `audit_events`.
  5. **Step 4b (Evaluate & Accept: `TRIAGING -> ACCEPTED`)**: Defender posts encrypted comments in either `RESEARCHER_ORG` (Class B) or `REVIEWER_INTERNAL` (Class C) using a fresh session key and `report_recipient_version`, selects the 8 CVSS v3.1 Base metrics, writes the mandatory **Researcher-Visible CVSS Explanation (`cvss_explanation_ciphertext`, Class B)** and optional **Internal CVSS Notes (`cvss_internal_notes_ciphertext`, Class C)**, and transitions the report from `TRIAGING` to `ACCEPTED` (`state_version + 1`).
  6. Server canonicalizes the CVSS v3.1 vector, authoritatively recalculates `cvss_score`, persists the `CVSS_ASSESSMENT_HISTORY` row (`seipdv2_body_sha256`), updates `REPORT` (`last_audit_seq_no`, `last_report_chain_hash`), and appends a hash-chained `AUDIT_EVENT` + `notification_outbox` entry.
* **Extensions**:
  * *2a. Passphrase incorrect*: Browser displays decryption error; private key remains locked.
  * *5a. Stale `report_recipient_version` (defender removed or key revoked concurrently)*: Server rejects with HTTP `409 Conflict`; browser refreshes active `REPORT_RECIPIENT` keyring (or blocks access if the current defender was removed).
  * *5b. Insufficient reproduction details*: Defender transitions `TRIAGING -> NEED_MORE_INFO` and posts a Class B clarification question, setting `info_timeout_due = now() + 14 days` (reset only when the researcher replies in `RESEARCHER_ORG`, which is guaranteed access to both the `1.0 MiB` active-report response sub-reserve and the `300 KiB` Priority-0 reserve allowlist; inside the client-owned outer transaction, `bbt_core.fn_process_researcher_response_or_pause` holds the `organizations -> reports` `FOR UPDATE` locks and runs the payload write inside a nested PL/pgSQL `BEGIN ... EXCEPTION WHEN SQLSTATE 'P0001'` subtransaction block so that if a recognized logical quota threshold rejects the payload with `413` or `507`, the inner block rolls back while retaining the outer `FOR UPDATE` locks, the `EXCEPTION` handler sets `app.quota_exempt_reason = 'CAPACITY_DEADLINE_PAUSE'` and updates `capacity_deadline_paused = true`, and the API client `COMMIT`s the outer transaction before returning `"deadline_paused": true`, blocking `CLOSED_INCOMPLETE` until capacity recovers).
  * *5c. Duplicate submission*: Defender links canonical parent `duplicate_of_report_id` (`FR-5.5a`, P1, locking `organizations` and then both `report_id` and `duplicate_of_report_id` in `ORDER BY id ASC FOR UPDATE` order) and transitions `TRIAGING -> DUPLICATE`.
  * *5d. Out of scope or invalid*: Defender selects Class A `rejection_code`, writes Class B `rejection_reason_ciphertext`, and transitions `TRIAGING -> REJECTED_INVALID`.
  * *5e. Automated scanner spam*: Defender transitions `NEW` or `TRIAGING -> REJECTED_SPAM` (reopenable only by `ORG_OWNER` with step-up MFA).
  * *5f. Operational risk acceptance*: `ORG_OWNER` (with step-up TOTP MFA) transitions `TRIAGING` or `ACCEPTED -> RISK_ACCEPTED` with Class C `risk_rationale_ciphertext` and `risk_review_date`.

#### Use Case UC-03: Propose Remediation Evidence, Confirm Deployment & Request Retest

* **Primary Actor**: Organization Triage Lead (`ORG_DEFENDER` active in `REPORT_RECIPIENT`).
* **Preconditions**: Report is in state `ACCEPTED`.
* **Main Success Scenario**:
  1. **Step 1 — Record Proposed Fix (`ACCEPTED -> FIX_PROPOSED`)**: Defender opens the Remediation Modal (`SCR-04`), selects `CODE_COMMIT` or `CONFIG_INFRASTRUCTURE`, and writes encrypted remediation notes (`remediation_notes_ciphertext`, Class B, checked against `report_recipient_version`).
     - *Path A (`CODE_COMMIT`)*: Defender inputs repository, `target_branch`, and 40-char `commit_sha`. Outside the DB transaction, server queries GitHub REST API v3 (`/commits/{sha}` and `/compare/{commit_sha}...{target_branch}`), verifies `status` is `ahead` or `identical`, and records `verified_branch_head_sha` and `github_signature_verified`.
     - *Path B (`CONFIG_INFRASTRUCTURE`)*: Defender supplies the redacted configuration diff/manifest (**`<= 160 KiB` [`163,840 bytes`] raw UTF-8 plaintext input**). Browser computes its 64-char SHA-256 `config_hash` via WebCrypto and encrypts the snapshot with OpenPGP compression disabled (`compression = openpgp.enums.compression.uncompressed`) as Class B `config_artifact_ciphertext` (**`<= 256 KiB` [`262,144 bytes`] armored ciphertext**, `FR-6.3`).
     Inside the short DB transaction (locking `2. organizations -> 5. reports -> 6. organization_audit_heads`), server creates `REMEDIATION_RECORD` (`remediation_attempt_no = N`, `remediation_record_id`, `status = 'PROPOSED'`) and atomically transitions report state `ACCEPTED -> FIX_PROPOSED` (`state_version + 1`).
  2. **Step 2 — Confirm Target Environment Deployment**: Once the patch is deployed, the defender records the target `deployment_env` (`Staging`, `Pre-Production`, or `Production`), `deployed_version`, and `deployed_at` timestamp on `remediation_record_id`.
  3. **Step 3 — Request Retest (`FIX_PROPOSED -> RETEST_PENDING`)**: Defender triggers "Request Retest." Server verifies `deployed_at != NULL` on the active `remediation_record_id`, atomically transitions `FIX_PROPOSED -> RETEST_PENDING` (`state_version + 1`, setting `retest_timeout_due = now() + 14 days`), records an `AUDIT_EVENT`, and enqueues a Class A metadata-only retest invitation referencing `remediation_attempt_no`.
* **Extensions**:
  * *1a. GitHub verification fails*: Server inspects rate-limit headers (`x-ratelimit-remaining == "0"`, `retry-after`) and response message (`FR-6.4`), returning `503 GITHUB_RATE_LIMIT_OR_OUTAGE` (for `429`, `5xx`, or rate-limit `403`), `422 GITHUB_AUTH_OR_PERMISSION_ERROR` (for non-rate-limit `401/403`), or `422 COMMIT_NOT_FOUND_OR_NOT_ANCESTOR` (for `404` or `behind`/`diverged`); **report remains in `ACCEPTED`**.
  * *2a. Proposed fix cancelled before deployment (`FIX_PROPOSED -> ACCEPTED`)*: Defender invokes `CANCEL_PROPOSED_FIX` with Class C `audit_justification_ciphertext`; `remediation_record_id` is marked `SUPERSEDED` and report returns to `ACCEPTED` (`FR-6.1d`).
  * *3a. Attempt to transition to `RETEST_PENDING` before recording deployment*: Server rejects with HTTP `400 Bad Request`.

#### Use Case UC-04: Execute Attested Retest Bound to Remediation Attempt

* **Primary Actor**: Ethical Security Researcher (`Hunter` / `Guest Hunter`) and Organization Triage Lead (`ORG_DEFENDER` in `REPORT_RECIPIENT`).
* **Preconditions**: Report is in state `RETEST_PENDING` with an active `remediation_record_id` (`remediation_attempt_no = N`).
* **Main Success Scenario**:
  1. Researcher inspects the linked `commit_sha` (or decrypts `config_artifact_ciphertext` and verifies `config_hash`) and `deployment_env` for `remediation_attempt_no = N` and re-tests the target asset.
  2. Researcher writes encrypted verification notes (`verification_notes_ciphertext`, Class B, checked against `report_recipient_version`, permitted to use the `1.0 MiB` active-report researcher response sub-reserve and the `300 KiB` Priority-0 reserve allowlist) and submits a `VERIFIED_RESEARCHER` attestation bound to `remediation_record_id` (if a guest submitter, signed with an OpenPGP v6 detached signature `X-Guest-Signature` over the canonical RFC 8785 JCS payload including `remediation_record_id` and single-use `nonce` per `FR-1.6f`).
  3. Inside one atomic transaction following the canonical lock order (**locking `2. organizations FOR UPDATE` -> `5. reports FOR UPDATE` -> `6. organization_audit_heads FOR UPDATE`** per `FR-7.1b`), checking `state == RETEST_PENDING`, `state_version`, `remediation_record_id`, and (for guests) inserting `(report_id, nonce)` into `guest_mutation_nonces`, the server persists `RETEST_EVIDENCE (fix_confirmed = true)`, marks `remediation_record_id.status = 'VERIFIED'`, transitions the report to `VERIFIED_RESEARCHER` (`state_version + 1`), updates `reports.last_audit_seq_no` / `last_report_chain_hash`, and appends a hash-chained `AUDIT_EVENT` (`report_seq_no`, `tenant_seq_no`, `org_commitment`) with a signed Audit Checkpoint Receipt.
* **Extensions**:
  * *2a. Vulnerability still exploitable (`RETEST_FAILED`)*: Researcher submits reproduction proof bound to `remediation_record_id`; server records `RETEST_EVIDENCE (fix_confirmed = false)`, marks `remediation_record_id.status = 'FAILED'`, and atomically transitions `RETEST_PENDING -> ACCEPTED` (`state_version + 1`). Any subsequent fix requires `remediation_attempt_no = N + 1`.
  * *2b. Internal verification (`VERIFIED_INTERNAL`)*: Defender in `REPORT_RECIPIENT` certifies the fix on `remediation_record_id` with `verification_notes_ciphertext` and `verifier_authored_fix` disclosure; state transitions to `VERIFIED_INTERNAL`.
  * *2c. Researcher unresponsive (`>= 14 days`)*: Defender in `REPORT_RECIPIENT` submits `audit_justification_ciphertext` (Class C) after `retest_timeout_due <= now() AND capacity_deadline_paused = false` and transitions `RETEST_PENDING -> CLOSED_UNVERIFIED_TIMEOUT`.
  * *2d. Simultaneous conflicting action (`409 Conflict`)*: If a researcher submits `RETEST_FAILED` while a defender simultaneously attempts `CLOSED_UNVERIFIED_TIMEOUT`, the second transaction fails the `state_version` check and returns HTTP `409 Conflict`.
  * *3a. Optional Post-Closure Follow-Up — Generate Redacted Closure Evidence Export (`FR-7.7`, P2)*: After closure (even if later non-transition audit events `M < j <= K` such as `MASTER_RECOVERY_FETCH_INITIATED` or `HISTORICAL_ACCESS_GRANTED` were appended after closure event `M`), an authorized defender opens `SCR-08` to export a signed `bbt-closure-export-v1` JSON (`.bbt-closure-export.json`) or PDF (`.bbt-closure-export.pdf` embedding `.bbt-closure-export.json` as an ISO 32000-2 Associated File) containing `export_payload` (`summary` with `closure_report_seq_no = M`, `report_chain[1..K]`, `unredacted_salts`, and privacy-safe `terminal_checkpoint_receipt` with `organization_slug` + `org_commitment`) and `export_signature` over `RFC8785_JCS(export_payload)`, verifiable offline without database access.

#### Use Case UC-05: Restore Guest or Registered User Keys, Rotate Guest Token & Re-Wrap Historical Keys

* **Primary Actor**: Account-Less Researcher (`Guest Hunter`), Registered Researcher (`Hunter`), Organization Defender (`ORG_DEFENDER`), or Organization Owner (`ORG_OWNER`).
* **Preconditions**: Actor possesses an OpenPGP v6 password-encrypted `.bbt-recovery.json` (guest) or `.bbt-user-keys.json` (registered user) file and its passphrase, OR is replacing a lost/compromised `USER_KEY`.
* **Main Success Scenario**:
  * **Branch A — Guest Key Restoration & Signature-Only Token Rotation (`GUEST`, `FR-1.6e–f`)**:
    1. Guest navigates to `/report/restore` (`SCR-10`) and selects their `.bbt-recovery.json` file.
    2. Browser reads the file strictly in local memory via `FileReader` (zero network upload) and decrypts `encrypted_recovery_bundle` via `openpgp.decrypt({ message, passwords: [passphrase] })`, verifying the SEIPDv2 AEAD authentication tag and inner `report_id`/`guest_actor_id`.
    3. Browser imports `armored_private_key` into `IndexedDB` and authenticates against `/report/track/BBT-RPT-XXXX` preserving durable `guest_actor_id` attribution.
    4. If the guest suspects their `access_token` was exposed (or if a previous rotation response was lost in transit), they click "Rotate Tracking Token," which invokes `POST /api/v1/reports/{id}/guest-token/rotate` (`bbt_core.fn_guest_rotate_token_by_sig`, requiring **only** `X-Guest-Signature` over `ROTATE_GUEST_TOKEN`, `nonce`, `issued_at`, `expires_at`—never requiring the old bearer token). The Node.js handler verifies the OpenPGP detached signature against `REPORT.guest_public_key`, encrypts the newly generated `{ report_id, guest_actor_id, access_token }` to `REPORT.guest_public_key` (`encrypted_guest_credentials_armored`), and calls `fn_guest_rotate_token_by_sig` (which unconditionally resets `app.definer_*` GUCs, locks `organizations -> reports -> organization_audit_heads`, verifies `guest_key_fingerprint`, rotates `guest_token_hash`, caches only `encrypted_guest_credentials_armored` in `guest_mutation_nonces`, and appends an `audit_events` row), after which the browser decrypts `encrypted_guest_credentials_armored` in memory and downloads an updated `.bbt-recovery.json`.
  * **Branch B — Registered User Personal Key Backup Restore (`HUNTER` / `ORG_DEFENDER` / `ORG_OWNER`, `FR-3.7`)**:
    1. Registered user logs in on a new device, navigates to `/settings/keys` (`SCR-10`), and selects their `.bbt-user-keys.json` Personal Key Backup file.
    2. Browser reads `.bbt-user-keys.json` locally via `FileReader`, unlocks `armored_private_key` using the user's passphrase (`s2kType = openpgp.enums.s2k.argon2`), verifies that `key_fingerprint` matches the user's active `USER_KEY` on the server, and stores the key in local `IndexedDB`.
  * **Branch C — Defender Key Loss Recovery (`grant-defender-access`, `CLASS_B_AND_C`, `FR-3.8b` Path 1)**:
    1. An `ORG_DEFENDER` who lost their browser storage without a `.bbt-user-keys.json` backup marks their old `key_id` as `REVOKED` (`FR-3.8a`), generates a new RFC 9580 v6 `USER_KEY (key_id_new)`, and exports a new `.bbt-user-keys.json`.
    2. Another active defender in `REPORT_RECIPIENT` (or MFA-authenticated `ORG_OWNER` via `POST /api/v1/reports/{id}/recovery-fetch` + offline Master Recovery Key) decrypts the session keys for **100% of Class B and Class C objects** on the report (including `CVSS_ASSESSMENT_HISTORY` Class B and Class C columns) in browser memory and submits the exact `{ object_type, object_id, field_name, prev_envelope_version, seipdv2_body_sha256, appended_pkesk_b64 }` manifest to `POST /api/v1/reports/{id}/grant-defender-access`.
    3. Inside a single transaction locking `organizations -> reports -> organization_audit_heads`, the server verifies the exact object ID/version manifest and unchanged `seipdv2_body_sha256` digests, appends the PKESK packets, activates `(report_id, user_id, key_id_new)` in `REPORT_RECIPIENT`, increments `report_recipient_version`, and logs `HISTORICAL_ACCESS_GRANTED`.
  * **Branch D — Registered Researcher Key Loss Recovery (`rewrap-researcher-key`, `CLASS_B_ONLY`, `FR-3.8b` Path 2)**:
    1. A registered `HUNTER` who lost their browser storage without a `.bbt-user-keys.json` backup marks their old `key_id` as `REVOKED`, generates a new `USER_KEY (key_id_new)`, and requests a Class B re-wrap on their submitted report.
    2. An authorized defender in `REPORT_RECIPIENT` (or MFA-verified `ORG_OWNER` via Master Recovery Key) re-wraps session keys for `key_id_new` **strictly across Class B objects only** (`REPORT` Class B columns, `CVSS_ASSESSMENT_HISTORY.cvss_explanation_ciphertext`, `RESEARCHER_ORG` messages, `REMEDIATION_RECORD`, `RETEST_EVIDENCE`, and `ATTACHMENT.encrypted_file_key_packet`—**strictly excluding all Class C objects**) and submits the manifest to `POST /api/v1/reports/{id}/rewrap-researcher-key`.
    3. Inside a single transaction locking `organizations -> reports -> organization_audit_heads`, the server verifies the exact `CLASS_B_ONLY` object ID/version manifest and unchanged `seipdv2_body_sha256` digests, updates `REPORT.submitter_key_id = key_id_new` (**without adding the researcher to `REPORT_RECIPIENT`**), increments `report_recipient_version`, and logs `RESEARCHER_KEY_REWRAPPED`.
* **Extensions**:
  * *A2a / B2a. Wrong passphrase or tampered file*: OpenPGP SEIPDv2 AEAD authentication fails in browser memory; import is aborted with zero network calls.
  * *C3a / D3a. Missing object ID, stale `prev_envelope_version`, or altered `seipdv2_body_sha256`*: Server rolls back the re-wrap transaction with HTTP `409 Conflict`.

#### Use Case UC-06: Onboard Tenant, Enroll MFA, Verify DNS & Sign `security.txt`

* **Primary Actor**: Organization Owner (`ORG_OWNER`).
* **Preconditions**: Authenticated user creating a new organization workspace.
* **Main Success Scenario**:
  1. Owner starts the Guided Onboarding Wizard (`SCR-07`), registers the organization slug (which initializes `organization_audit_heads` with `last_seq_no = 0`), and completes mandatory **TOTP MFA enrollment** (`FR-1.3c`).
  2. Owner publishes the `_bbt-challenge.<domain>` DNS TXT record verified by the server (`FR-2.5`).
  3.   * `GET /repos/{owner}/{repo}/compare/{commit_sha}...{target_branch}` (`BASE...HEAD` where `base = commit_sha`, `head = target_branch`): Verifies that the proposed fix commit is an ancestor of (or identical to) the target branch tip (`status IN ('ahead', 'identical')` and `behind_by == 0`), recording `verified_branch_head_sha` and `verified_at`.
  * **Rate-Limit Header Inspection**: Inspects `x-ratelimit-remaining` and `retry-after` headers on all `403` and `429` responses to distinguish rate-limit throttling (`503 GITHUB_RATE_LIMIT_OR_OUTAGE`) from credential/permission failures (`422 GITHUB_AUTH_OR_PERMISSION_ERROR`).
* **GitHub Actions Hourly Scheduled Workflow (`lifecycle-cron.yml`)**: Invokes `POST /api/cron/lifecycle-evaluate` every hour (`0 * * * *`) authenticated strictly via **`X-Cron-Timestamp`** (`<= 300s` replay window) and **`X-Cron-Signature: sha256=<HMAC_SHA256(CRON_HMAC_SECRET, timestamp + "." + raw_body)>`**, with automatic `workflow_dispatch` continuation whenever **`has_more_backlog == true`** (`has_more_deadline_backlog OR has_more_r2_backlog OR has_more_purge_backlog`, `Section 2.6`).
* **DNS Resolver (Node.js `dns.promises`)**: `resolveTxt('_bbt-challenge.<domain>')` verifying domain ownership tokens.
* **Resend / Postmark Transactional Email API**: Dispatches Class A metadata-only notifications and signed Audit Checkpoint Receipts (`organization_slug` + `org_commitment`) from `notification_outbox` over TLS 1.3 with exponential backoff retry.
* **Cloudflare R2 Object Storage (S3-Compatible API — Executed Outside Database Transactions)**: `PutObjectCommand` (with `Content-Length` and `If-None-Match: *`), `HeadObjectCommand` (executed outside DB transactions before `POST /api/v1/reports` Tx), `GetObjectCommand`, and `DeleteObjectCommand` (executed in Phase 2 of each sequential cron batch outside DB transactions at concurrency `5` with `1,000 ms` per-request timeout and `11,000 ms` invocation cutoff, with storage credited in Phase 3 immediately after each batch's Phase 2 strictly when `status = 'DELETING' AND claim_id = :claim_id` transitions to `'DELETED'`).

## 6. Quantifiable Non-Functional Requirements (Latency, Security & Uptime)

All performance, availability, and recovery thresholds below are established as **provisional engineering acceptance targets** to be empirically measured under the explicitly specified reference conditions during Phase 4 (Quality Assurance & Verification):

* **NFR-01 (Server API Latency Target & Reference Conditions)**:
  * **Target**: `p95 <= 300 ms` (warm invocation) and `p95 <= 1,200 ms` (serverless cold start) for non-cryptographic API endpoints (`GET /api/v1/programs`, `GET /api/v1/reports`, state transition `PATCH` routes).
  * **Measurement Conditions**: Measured via k6 running 20 concurrent virtual users (VUs) over 60 seconds against a Node.js 22 LTS deployment connected to Neon PostgreSQL 16 (same regional zone, pooled via PgBouncer) with a seeded dataset of 10 organizations and 500 encrypted reports.
* **NFR-02 (Client Cryptographic Latency Benchmark & Reference Conditions)**:
  * **Target**: `< 50 ms` for bare RFC 9580 v6 Curve25519 keypair generation; `~200–400 ms` for Argon2id S2K key unlocking (`s2kType = openpgp.enums.s2k.argon2`, `passes = 3, parallelism = 4, memoryExponent = 16 [64 MiB]`); and `<= 1,500 ms` for end-to-end multi-recipient payload encryption or decryption.
  * **Measurement Conditions**: Measured via Playwright `performance.now()` over 50 iterations in Chromium 120+ on reference hardware (4-core / 8-thread x86_64 CPU @ 2.8 GHz or Apple M1, 16 GB RAM), encrypting a `100 KiB` Markdown payload across `5` recipient subkeys (`3` `REPORT_RECIPIENT` keys + `1` `recovery_public_key` + `1` submitter key), measured separately from network transfer and Argon2id unlock time.
* **NFR-03 (Security — Zero Cross-Tenant & Unauthorized Role Leakage under `FORCE ROW LEVEL SECURITY` & GUC-Reset Definer Functions)**:
  * **Target**: `0` unauthorized cross-tenant rows returned and `100%` enforcement of **Table 2.2** across all integration test queries (`TC-SEC-01`, `TC-AUTH-02`).

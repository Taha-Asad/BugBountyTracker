### 2.2 Formal Textual Use Case Specifications (`UC-01` to `UC-07`)

#### Use Case `UC-01`: Submit Encrypted Vulnerability Report & Generate Authenticated Recovery Package
* **Primary Actor**: Ethical Security Researcher (`Registered Hunter` or `Account-Less Guest Hunter`).
* **Preconditions**: Researcher is viewing an organization's active public program page (or holds a valid private program invitation token `token_hash`).
* **Main Success Scenario**:
  1. Researcher selects an in-scope target asset (`asset_scope`), selects a coarse Class A `operational_label` enum, enters the specific vulnerability title, reproduction steps, and optional PoC attachments (`<= 3` files, `<= 25 MiB` encrypted size each, `<= 50 MiB` total report size).
  2. Browser configures `OpenPGP.js v6` (`v6Keys = true`, `s2kType = argon2`, `aeadProtect = true`) and fetches the program's active `PROGRAM_DEFENDER` key versions (`recipient_set_version`) plus `recovery_public_key`.
     - **Branch A (Account-Less Guest Submitter)**: Browser generates an ephemeral RFC 9580 v6 Curve25519 keypair in memory (`< 50 ms` target) and prompts for (or generates) a Guest Recovery Passphrase.
     - **Branch B (Registered Hunter)**: Browser unlocks the researcher's existing RFC 9580 v6 keypair from `IndexedDB` (`key_id`).
  3. Browser completes Cloudflare Turnstile CAPTCHA once and calls `POST /api/v1/submission-sessions` to obtain a 30-minute `submission_session_token` (`status = OPEN`).
  4. *Optional (`«extend»` — if attachments present)*: For each attachment (`1..3`), browser encrypts the file into an RFC 9580 OpenPGP SEIPDv2 binary message using a fresh 256-bit key `K_file`, requests `POST /api/uploads/presign` (creating a 15-minute `upload_reservations` row in `status = RESERVED` after checking `19.0 MiB` new-intake DB cap, `1.0 GiB` tenant R2 cap, and `9.5 GiB` `cluster_storage_state` cap), and uploads the ciphertext directly to Cloudflare R2 (`If-None-Match: *`).
  5. Browser encrypts all Class B fields (`title_ciphertext`, description, reproduction steps, impact, and detached `K_file` packets under the Authoritative Class B Recipient Rule) into a multi-recipient OpenPGP v6 message for the active `PROGRAM_DEFENDER` key versions, `recovery_public_key` (tagged with `recovery_key_fingerprint`), and the submitter's key, then dispatches `POST /api/v1/reports` (returning `201 Created`).
  6. Server verifies `HeadObjectCommand` outside the DB transaction (if attachments exist); for guest submissions, encrypts `{ report_id, guest_actor_id, access_token }` to `guest_public_key` (`encrypted_guest_credentials_armored`); then inside an atomic transaction following the canonical lock order (`organizations -> programs -> submission_sessions -> reports -> organization_audit_heads`) atomically transitions `submission_sessions` `OPEN -> CONSUMED` storing `cached_response_json` (`encrypted_guest_credentials_armored`, never raw `access_token`, 30m TTL), verifies `recipient_set_version`, binds `upload_reservations` (`RESERVED -> BOUND`), inserts `REPORT` (`NEW`, `state_version = 1`, `report_recipient_version = 1`, `last_audit_seq_no = 1`), snapshots `PROGRAM_DEFENDER` (`user_id`, `key_id`) into `REPORT_RECIPIENT`, and appends `report_seq_no = 1` / `tenant_seq_no` (`report_chain_hash` + `event_digest` + `tenant_row_hash`) to `audit_events` + `notification_outbox`.
  7. **Post-Submission Key Persistence**:
     - **Branch A (Guest Submitter)**: Browser decrypts `encrypted_guest_credentials_armored` in memory to extract `access_token`, encrypts `{ access_token, ephemeral_private_key_armored }` via `openpgp.encrypt({ passwords: [passphrase] })` (`SYMENC+SEIPDv2`, Argon2id `0x04`) into `.bbt-recovery.json`, stores the key in `IndexedDB`, displays `/report/track/BBT-RPT-XXXX#token=<secret>`, and scrubs the URI fragment via `window.history.replaceState`.
     - **Branch B (Registered Hunter)**: Browser navigates directly to `/hunter/submissions/BBT-RPT-XXXX`.
* **Extensions**:
  * *2a. Organization public key missing or invalid*: Browser blocks submission and alerts user.
  * *3a / 6a. Rate limit (`> 5/hr/IP`) or storage quota (`> 95%` [`19.0 MiB`] new-intake sub-cap of `20 MiB` DB intake / `1.0 GiB` tenant R2 / `9.5 GiB` cluster R2) exceeded*: Server rejects with HTTP `429 Too Many Requests` or `413 Payload Too Large` (preserving the `1.0 MiB` active-report researcher-response sub-reserve).
  * *5a. Stale `recipient_set_version`*: Server returns HTTP `409 Conflict` with updated keyring; browser re-encrypts the text payload and `K_file` packets (without re-uploading R2 attachment blobs) and retries automatically.
  * *6b. Replayed `submission_session_token` with different payload*: Server returns HTTP `409 Conflict` (`SUBMISSION_SESSION_ALREADY_CONSUMED`).

#### Use Case `UC-02`: Decrypt, Claim for Triage & Score Vulnerability Report
* **Primary Actor**: Organization Triage Lead (`ORG_DEFENDER` in `REPORT_RECIPIENT`).
* **Preconditions**: Authenticated with `ORG_DEFENDER` role and listed in `REPORT_RECIPIENT` (`revoked_at IS NULL`) for the report; report is in state `NEW` or `TRIAGING`.
* **Main Success Scenario**:
  1. Defender opens `/dashboard/reports/[id]`. Browser fetches the ciphertext record (`state_version`, `report_recipient_version`) and retrieves the defender's encrypted private key from `IndexedDB`.
  2. Defender enters their local encryption passphrase to unlock the Argon2id S2K-protected private key (`~200–400 ms` intentional delay).
  3. Browser decrypts `title_ciphertext` and `encrypted_payload` in memory, sanitizes the Markdown AST via `rehype-sanitize`, and renders sanitized HTML.
  4. **Step 4a (Claim Intake: `NEW -> TRIAGING`)**: If the report is in `NEW`, the defender clicks "Begin Triage," locking `organizations` then `reports` (`state_version + 1`), transitioning `NEW -> TRIAGING`, and recording the assigned triager in `audit_events`.
  5. **Step 4b (Evaluate & Accept: `TRIAGING -> ACCEPTED`)**: Defender posts encrypted comments in either `RESEARCHER_ORG` (Class B) or `REVIEWER_INTERNAL` (Class C) checking `report_recipient_version`, selects the 8 CVSS v3.1 Base metrics, writes mandatory researcher-visible `cvss_explanation_ciphertext` (Class B) and optional `cvss_internal_notes_ciphertext` (Class C), and transitions `TRIAGING -> ACCEPTED` (`state_version + 1`).
  6. Server recalculates and persists canonical `cvss_vector`, `cvss_score`, `cvss_explanation_ciphertext`, `cvss_internal_notes_ciphertext`, and a `CVSS_ASSESSMENT_HISTORY` row (`assessment_seq_no`), and appends a hash-chained `AUDIT_EVENT` (`report_chain_hash` + `event_digest` + `tenant_row_hash`) while updating `reports.last_audit_seq_no` and `reports.last_report_chain_hash`.
* **Extensions**:
  * *2a. Passphrase incorrect*: Browser displays decryption error; private key remains locked.
  * *5a. Insufficient reproduction details*: Defender transitions `TRIAGING -> NEED_MORE_INFO` and posts a Class B clarification question (auto-transitions to `CLOSED_INCOMPLETE` after `>= 14 days` of researcher inactivity unless `capacity_deadline_paused = true`; when a researcher response is rejected by a recognized logical quota code (`413` or `507`) inside the client-owned outer transaction, `fn_process_researcher_response_or_pause` catches `SQLSTATE 'P0001'` in its nested PL/pgSQL `BEGIN ... EXCEPTION` subtransaction block while retaining the outer `organizations -> reports` `FOR UPDATE` locks, sets `capacity_deadline_paused = true` under `app.quota_exempt_reason = 'CAPACITY_DEADLINE_PAUSE'`, and the API client `COMMIT`s the outer transaction before returning `"deadline_paused": true`).
  * *5b. Duplicate submission*: Defender links canonical parent `duplicate_of_report_id` (locking both reports in `ORDER BY id ASC FOR UPDATE`) and transitions `TRIAGING -> DUPLICATE` (`FR-5.5a`).
  * *5c. Out of scope or invalid*: Defender selects Class A `rejection_code`, writes Class B `rejection_reason_ciphertext`, and transitions `TRIAGING -> REJECTED_INVALID`.
  * *5d. Automated scanner spam*: Defender transitions `NEW` or `TRIAGING -> REJECTED_SPAM` (reopenable only by `ORG_OWNER` with TOTP MFA if misclassified).
  * *5e. Operational risk acceptance*: `ORG_OWNER` (with TOTP MFA step-up) transitions `TRIAGING` or `ACCEPTED -> RISK_ACCEPTED` with Class C `risk_rationale_ciphertext` and `risk_review_date`.

#### Use Case `UC-03`: Propose Remediation Evidence, Confirm Deployment & Request Retest
* **Primary Actor**: Organization Triage Lead (`ORG_DEFENDER` in `REPORT_RECIPIENT`).
* **Preconditions**: Report is in state `ACCEPTED`.
* **Main Success Scenario**:
  1. **Step 1 — Record Proposed Fix (`ACCEPTED -> FIX_PROPOSED`)**: Defender opens the Remediation Modal (`SCR-04`), selects `CODE_COMMIT` or `CONFIG_INFRASTRUCTURE`, and writes encrypted remediation notes (`remediation_notes_ciphertext`, Class B, checking `report_recipient_version`).
     - *Path A (`CODE_COMMIT`)*: Defender inputs repository, `target_branch`, and 40-char `commit_sha`. Server queries GitHub REST API v3 (`/commits/{sha}` and `/compare/{commit_sha}...{target_branch}`), verifies `status` is `ahead` or `identical`, and records `verified_branch_head_sha` and `github_signature_verified`.
     - *Path B (`CONFIG_INFRASTRUCTURE`)*: Browser computes a 64-char SHA-256 `config_hash` via WebCrypto over the normalized configuration snapshot (`<= 160 KiB` [`163,840 bytes`] incompressible UTF-8 plaintext input with OpenPGP compression disabled) and encrypts the snapshot as Class B `config_artifact_ciphertext` (`<= 256 KiB` [`262,144 bytes`] armored ciphertext).
     Server locks `organizations` then `reports`, creates `REMEDIATION_RECORD` (`remediation_attempt_no = N`, `remediation_record_id`), and atomically transitions report state `ACCEPTED -> FIX_PROPOSED` (`state_version + 1`).
  2. **Step 2 — Confirm Target Environment Deployment**: Once the patch is deployed, the defender records the target `deployment_env` (`Staging`, `Pre-Production`, or `Production`), `deployed_version`, and `deployed_at` timestamp on `remediation_record_id`.
  3. **Step 3 — Request Retest (`FIX_PROPOSED -> RETEST_PENDING`)**: Defender triggers "Request Retest." Server verifies `deployed_at != NULL` on the active `remediation_record_id`, atomically transitions `FIX_PROPOSED -> RETEST_PENDING` (`state_version + 1`), records an `AUDIT_EVENT`, and enqueues a Class A metadata-only retest invitation referencing `remediation_attempt_no`.
* **Extensions**:
  * *1a. GitHub commit verification fails*: Server inspects `x-ratelimit-remaining` / `retry-after` headers (`FR-6.4`) and returns `422 GITHUB_AUTH_OR_PERMISSION_ERROR`, `422 COMMIT_NOT_FOUND_OR_NOT_ANCESTOR`, or `503 GITHUB_RATE_LIMIT_OR_OUTAGE`; report remains in `ACCEPTED` (no unverified manual code patch digest fallback is permitted).
  * *2a. Proposed fix superseded before retest (`CANCEL_PROPOSED_FIX`)*: Defender cancels `remediation_record_id` (`superseded = true`) and transitions `FIX_PROPOSED -> ACCEPTED` (`state_version + 1`).
  * *3a. Attempt to transition to `RETEST_PENDING` before recording deployment*: Server rejects with HTTP `400 Bad Request`.

#### Use Case `UC-04`: Execute Attested Retest Bound to Remediation Attempt & Export Closure Evidence
* **Primary Actor**: Ethical Security Researcher (`Hunter` / `Guest Hunter`) and Organization Triage Lead (`Defender`).
* **Preconditions**: Report is in state `RETEST_PENDING` with an active `remediation_record_id` (`remediation_attempt_no = N`).
* **Main Success Scenario**:
  1. Researcher inspects the linked `commit_sha` / (`config_hash` + decrypted `config_artifact_ciphertext`) and `deployment_env` for `remediation_attempt_no = N` and re-tests the target asset.
  2. Researcher writes encrypted verification notes (`verification_notes_ciphertext`, Class B, checking `report_recipient_version`) and submits a `VERIFIED_RESEARCHER` attestation bound to `remediation_record_id` (authenticated via canonical RFC 8785 JCS + OpenPGP v6 detached signature `X-Guest-Signature` verified in Node.js before single-use `nonce` consumption in SQL if a guest submitter).
  3. Inside an atomic transaction locking `organizations`, `reports`, and `organization_audit_heads` and checking `state == RETEST_PENDING` and `state_version`, the server persists `RETEST_EVIDENCE` (linked to `remediation_record_id`), transitions the report to `VERIFIED_RESEARCHER` (`state_version + 1`), and appends a hash-chained `AUDIT_EVENT` (`report_chain_hash` + `event_digest` + `tenant_row_hash`) with a signed checkpoint receipt.
* **Extensions**:
  * *2a. Vulnerability still exploitable (`RETEST_FAILED`)*: Researcher submits reproduction proof bound to `remediation_record_id`; server records `RETEST_EVIDENCE (fix_confirmed = false)` and atomically transitions `RETEST_PENDING -> ACCEPTED` (`state_version + 1`). Any subsequent fix requires `remediation_attempt_no = N + 1`.
  * *2b. Internal verification (`VERIFIED_INTERNAL`)*: Defender certifies the fix on `remediation_record_id` with `verification_notes_ciphertext` and `verifier_authored_fix` disclosure; state transitions to `VERIFIED_INTERNAL`.
  * *2c. Researcher unresponsive (`>= 14 days`)*: Defender submits `audit_justification_ciphertext` (Class C) and transitions `RETEST_PENDING -> CLOSED_UNVERIFIED_TIMEOUT` (blocked if `capacity_deadline_paused = true`).
  * *2d. Simultaneous conflicting action (`409 Conflict`)*: If a researcher submits `RETEST_FAILED` while a defender simultaneously submits `CLOSED_UNVERIFIED_TIMEOUT`, the second transaction fails the `state_version` check and returns HTTP `409 Conflict`.
  * *3a. Optional [P2] Redacted Closure Evidence Export (`FR-7.7`)*: Defender or `ORG_READONLY` opens `SCR-08` and generates a self-contained Class A Redacted Closure Evidence Export (`bbt-closure-export-v1`, PDF with embedded `.bbt-closure-export.json` Associated File or standalone JSON) containing `{ schema, export_payload: { summary, report_chain, unredacted_salts, terminal_checkpoint_receipt }, export_signature }` where `export_signature` signs `RFC8785_JCS(export_payload)`, `org_commitment` replaces internal `org_id`, `summary.closure_report_seq_no = M` (`1 <= M <= K`) identifies the active closure event `report_chain[M]`, and the standalone verifier checks Summary-to-Chain equality against `report_chain[M]`, verifies `from_state == terminal_state AND to_state == terminal_state` for any post-closure events (`M < j <= K`), and anchors `report_chain[1..K]` to `terminal_checkpoint_receipt`.

#### Use Case `UC-05`: Restore Guest or Registered User Keys, Rotate Guest Token & Execute Separated Key Recovery
* **Primary Actor**: Account-Less Researcher (`Guest Hunter`) or Registered User (`Hunter` / `Defender` / `Owner`).
* **Preconditions**: Actor possesses an RFC 9580 OpenPGP v6 encrypted `.bbt-recovery.json` (guest) or `.bbt-user-keys.json` (registered user) file and its recovery passphrase, or `ORG_OWNER` executes an audited Master Recovery Key ceremony.
* **Main Success Scenario**:
  - **Branch A — Account-Less Guest Restore & Token Rotation (`FR-1.6c–f`)**:
    1. Guest navigates to `/report/restore` (`SCR-10`) and selects their `.bbt-recovery.json` file.
    2. Browser reads the file strictly in local memory via `FileReader` (zero network upload), verifies the OpenPGP `SYMENC+SEIPDv2` S2K specifier is `0x04` (Argon2id), and runs `openpgp.decrypt({ passwords: [passphrase] })`.
    3. Browser parses `{ access_token, ephemeral_private_key_armored }`, imports the private key into `IndexedDB`, and authenticates against `/report/track/BBT-RPT-XXXX` preserving durable `guest_actor_id` attribution.
    4. If the guest suspects their `access_token` was exposed (or if a previous rotation response was lost in transit), they click "Rotate Tracking Token," which calls `POST /api/v1/reports/{id}/guest-token/rotate` (`fn_guest_rotate_token_by_sig`) with a canonical RFC 8785 JCS `ROTATE_GUEST_TOKEN` envelope signed by `X-Guest-Signature` (verified in Node.js using `guest_public_key`, requiring only the Ed25519 private key and not the invalidated bearer token), invalidates the old `guest_token_hash`, returns `encrypted_guest_credentials_armored` cached in `guest_mutation_nonces.response_body_json` (5m TTL, zero raw token persistence), and downloads a newly encrypted `.bbt-recovery.json` package.
  - **Branch B — Registered User Personal Key Backup Restore & Separated Key-Loss Recovery (`FR-3.7`, `FR-3.8b`)**:
    1. Registered user logs into a new device, navigates to `/settings/keys` (`SCR-10`), and selects their `.bbt-user-keys.json` file.
    2. Browser reads `.bbt-user-keys.json` locally via `FileReader`, verifies that `public_key_fingerprint` matches the user's active server-registered `USER_KEY (key_id)` and that the secret key packet uses S2K `0x04` (Argon2id) + AEAD (`254`), unlocks the secret key with the user's passphrase, and stores it in `IndexedDB`.
    3. *Alternative (Total Key Loss + Passphrase Loss)*: User registers a new `USER_KEY (key_id_new)`. For an organization defender, `ORG_OWNER` executes **Path 1 (`POST /api/v1/reports/{id}/grant-defender-access`, `CLASS_B_AND_C`)** to re-wrap Class B + Class C objects (including `CVSS_ASSESSMENT_HISTORY`) and activate `REPORT_RECIPIENT`. For a registered researcher (`HUNTER`), `ORG_OWNER` executes **Path 2 (`POST /api/v1/reports/{id}/rewrap-researcher-key`, `CLASS_B_ONLY`)**, which re-wraps **exclusively Class B objects**, never touches Class C internal notes, never adds the researcher to `REPORT_RECIPIENT`, updates `REPORT.submitter_key_id = key_id_new`, and increments `report_recipient_version`.

#### Use Case `UC-06`: Onboard Tenant, Verify DNS, Configure Master Recovery Key & Sign `security.txt`
* **Primary Actor**: Organization Owner (`ORG_OWNER`).
* **Preconditions**: Authenticated user creating or configuring an organization workspace with TOTP MFA enabled (`FR-1.3c`).
* **Main Success Scenario**:
  1. Owner completes the Guided Onboarding Wizard (`SCR-07`), which initializes `organizations` (`org_commitment_salt`) and `organization_audit_heads (last_seq_no = 0)`, and publishes the `_bbt-challenge.<domain>` DNS TXT record verified by the server (`FR-2.5`).
  2. Browser configures `OpenPGP.js v6` (`v6Keys = true`, `s2kType = argon2`, `aeadProtect = true`) and generates the owner's Curve25519 keypair plus the offline **Organization Master Recovery Keypair** (`recovery_public_key`, `recovery_key_fingerprint`).
  3. Owner downloads the Argon2id-encrypted private Master Recovery Key file and completes the mandatory in-browser test decryption challenge (`Uint8Array` buffers zeroized immediately after verification).
  4. Owner assigns authorized defenders (`user_id`, `key_id`) to `PROGRAM_DEFENDER` (incrementing `recipient_set_version`) and cleartext-signs the generated RFC 9116 `security.txt` manifest in-browser for publication at `/.well-known/security.txt`.

#### Use Case `UC-07`: Enforce Scheduled SLA / Inactivity Timers & Verify Hash-Chained Audit Ledger
* **Primary Actor**: Organization Reviewer (`ORG_DEFENDER`), Read-Only Auditor (`ORG_READONLY`), or Hourly GitHub Actions Cron (`lifecycle-cron.yml`).
* **Preconditions**: Active vulnerability reports exist within the tenant workspace.
* **Main Success Scenario**:
  1. Hourly GitHub Actions workflow (`0 * * * *`) invokes `POST /api/cron/lifecycle-evaluate`, verified in Node.js via constant-time HMAC-SHA256 (`X-Cron-Timestamp` + `X-Cron-Signature` using `CRON_HMAC_SECRET`), and executes up to `3` sequential `Phase 1 -> Phase 2 -> Phase 3` batches (`<= 30` R2 objects, `<= 150` overdue deadlines, and `<= 600` expired session/nonce rows per table within `< 15s` — starting a new batch only when `elapsed_ms <= 8,000 ms`, aborting R2 I/O at `t == 11,000 ms`, and reserving `11,000 ms .. 15,000 ms` [`4,000 ms`] as invocation headroom for the final batch's Phase 3) with automatic `workflow_dispatch` continuation when `has_more_backlog == true` (`has_more_deadline_backlog OR has_more_r2_backlog OR has_more_purge_backlog`):
     - **Phase 1 (Short DB Tx #1 — `fn_cron_evaluate_overdue_deadlines(p_r2_claim_limit => 10, p_deadline_limit => 50, p_purge_limit => 200)` under `connectionTimeoutMillis = 1,000 ms`, `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)**: Acquires `pg_try_advisory_xact_lock(889001)`, evaluates up to `50` overdue (`<= now()`) `sla_triage_due` and `sla_remediation_due` deadlines and `NEED_MORE_INFO` reports with researcher inactivity `>= 14 days` (where `capacity_deadline_paused == false` -> `CLOSED_INCOMPLETE`), purges up to `200` expired `submission_sessions` (`expires_at < now()`) and up to `200` expired `guest_mutation_nonces` (`expires_at < now()`) using `ORDER BY expires_at ASC LIMIT 200 FOR UPDATE SKIP LOCKED`, claims up to `10` expired `upload_reservations` (`(status IN ('RESERVED', 'DELETE_FAILED') AND expires_at <= now()) OR (status = 'DELETING' AND claim_expires_at <= now())`) into `status = 'DELETING'` with a fresh `claim_id = gen_random_uuid()` and 2-minute lease `claim_expires_at = now() + interval '2 minutes'`, and returns `{ claimed_r2_rows, has_more_deadline_backlog, has_more_r2_backlog, has_more_purge_backlog }`.
     - **Phase 2 (External R2 Deletion Outside DB Tx)**: Node.js issues `DeleteObjectCommand` at bounded concurrency `5` (`2` waves of `5`) with a `1,000 ms` per-request timeout and an absolute invocation cutoff at `t == 11,000 ms` (`AbortSignal.any([AbortSignal.timeout(1000), AbortSignal.timeout(Math.max(0, 11000 - elapsed_ms))])`) while holding zero PostgreSQL locks.
     - **Phase 3 (Immediate Per-Batch DB Tx #2 — `fn_cron_finalize_r2_deletions` under `connectionTimeoutMillis = 1,000 ms`, `lock_timeout = '250ms'`, `statement_timeout = '800ms'`)**: Executed immediately after the current batch's Phase 2 finishes, matches `WHERE reservation_id = :res_id AND status = 'DELETING' AND claim_id = :claim_id`, marks succeeded keys `status = 'DELETED'`, and decrements `r2_bytes_used` and `cluster_storage_state.total_r2_allocated_bytes` strictly when `ROW_COUNT == 1` on the `'DELETING' -> 'DELETED'` transition (or marks `'DELETE_FAILED'` for retry, or leaves rows `'DELETING'` with `has_more_r2_backlog = true` for 2-minute lease-expiry reclaim if Phase 3 times out or fails to commit).
  2. Approaching or breached SLA targets enqueue Class A metadata-only email and webhook alerts in `notification_outbox` containing a signed Audit Checkpoint Receipt (`org_commitment`).
  3. Defenders and `ORG_READONLY` auditors inspect `/dashboard/audit` (`SCR-12`) to verify gapless `tenant_seq_no` ordering, universal `event_digest` + `tenant_row_hash` and `report_chain_hash` continuity, and Ed25519 checkpoint signatures against `/api/v1/audit/checkpoint-keys`.
